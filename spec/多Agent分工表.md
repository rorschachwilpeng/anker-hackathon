# 多 Agent 分工表

最后更新：2026-09-17

## 目的

本表管理项目调研阶段的三个 Codex 任务：总控任务负责收口，两条赛事任务各自建立事实基础。这里的 Agent 是建设项目的 Codex 任务，不是参赛产品内部的 Agent 架构。

## 共同边界

- 共同事实源优先级：用户最新决定、根目录 `AGENTS.md`、已确认的 `spec/`、公开一手资料、其他二手资料。
- 联网调研优先使用官方赛事页面、官方文档、原始项目仓库和数据集发布方。
- 不使用 PKFARE 或 Anker 的内部数据，不把模拟能力写成真实能力。
- 两个调研 Agent 不替用户决定最终赛道、故事线、产品范围或技术架构。
- 未经用户明确授权，不报名、不提交作品、不联系外部人员。

## 主控需要知道的颗粒度

总控 Agent 不是日常任务登记员。专项 Agent 对职责内的检索、判断、草稿和普通成果独立负责；只有当总控需要采取动作，或项目的方向、状态和风险发生变化时，才即时向上同步。

| 总控需要知道 | 无需即时知道 |
| --- | --- |
| 会改变共同 Spec、赛道、故事线、优先级或验收标准的结论 | 检索过程、搜索词、逐条来源和普通阅读笔记 |
| 需要用户在互斥方案中拍板的选择 | 尚未成熟的想法、局部草稿和措辞调整 |
| 必须跨 Agent 交接、依赖或解决的冲突 | 职责范围内可独立解决的小问题 |
| 没有替代路径的阻塞、外部期限或重大风险 | 普通进展、常规提交和不影响他人的任务完成 |
| 阶段成果已经齐备，需要验收或决定是否进入下一阶段 | 专项目录内正式但未达到里程碑的中间成果 |

## 四类向上汇报

专项 Agent 只有命中以下一种类型时，才向总控 Agent 发起即时同步。

| 汇报类型 | 触发条件 | 总控动作 |
| --- | --- | --- |
| `请决策` | 存在两个以上互斥方案，选择会改变共同 Spec、赛道、故事线、范围、架构或验收标准，且超出专项 Agent 授权 | 组织用户确认并记录决定 |
| `请协调` | 必须由另一 Agent 提供输入、接收交付、停止使用旧结论，或共同解决职责冲突 | 指定主责、交付物、顺序和验收标准 |
| `请升级` | 没有替代路径的阻塞；比赛期限受威胁；新证据使既有结论失效；出现安全、隐私、许可、授权或真实性风险 | 控制风险、排除阻塞或调整计划 |
| `请验收` | 预先约定的阶段交付已经完成，证据齐备，需要决定通过、退回或进入下一阶段 | 对照成功标准检查成果并作出阶段判断 |

每次向上汇报只包含六项：汇报类型、一句话结论、触发事实、证据位置、影响范围、总控需要采取的动作。无法归入四类，或总控无需采取动作的，不即时向上同步。

## 跨 Agent 协作

1. 发起 Agent 下发任务时写清目标、输入、输出、成功标准、允许写入范围，以及结果回复对象。
2. 接收 Agent 不发送纯“收到”消息；只在缺少会改变执行方向的输入、命中四类汇报，或已有可验收结果时回传。
3. 发起 Agent 负责验收结果；信息不足时沿用原任务继续追问，不能把未验收成果直接升级为共同结论。
4. 两个调研 Agent 独立工作，不在同一文件中并行写入。跨赛事可复用的判断经总控验收后进入 `spec/`，赛事专属事实留在各自调研目录。
5. 当两边结论冲突时，先保留差异。只有涉及方向决策、职责冲突、共同 Spec、主控级里程碑或重大风险时，才同步总控处理。
6. 用户确认核心命题和深圳故事线后，再进入需求定义与方案设计。
