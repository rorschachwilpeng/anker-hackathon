# 多 Agent 分工表

最后更新：2026-09-19

## 目的

本表管理 Anker 智能服务 Agent 的产品—技术双线程协作。当前只启用两个长期执行线程：Product Lead 与 Technical Builder。总控 Agent 保留跨项目治理职责，但不计入日常产品—技术双线程，也不介入双方职责内的细节决策。

这里的 Agent 是建设项目的 Codex 任务，不是参赛产品内部的 Agent 架构。角色、决策和交付以仓库文档为准，不依赖聊天摘要。

## 决策边界

| 问题 | Product Lead | Technical Builder | 总控 Agent |
| --- | --- | --- | --- |
| 为什么做、为谁解决什么问题 | 决定 | 提供技术约束，不改写目标 | 仅在跨项目冲突时协调 |
| 做什么、做到什么程度 | 决定产品范围和验收口径 | 反馈可行性、成本与风险 | 仅处理无人承接或职责冲突 |
| 如何实现 | 确认方案是否满足产品目标 | 决定技术方案与实现路径 | 不介入 |
| 人力、工期与技术风险 | 不单方面承诺 | 负责评估并提供依据 | 重大风险影响赛事期限时升级处理 |
| 技术上不可行或成本过高 | 从缩减选项中做产品取舍 | 返回约束、替代路径和缩减选项 | 仅在双方无法收敛时协调 |
| 是否进入开发 | 确认 MVP 产品范围已锁定 | 确认技术接手审计通过 | 不代替双方放行 |
| 是否通过验收 | 按产品 Spec 判断业务与体验结果 | 提供技术验证证据 | 只检查流程、证据与责任是否完整 |

任何一方都不能把自己的专业判断扩张为对另一方职责的最终决定。

## 输入、输出与交接节点

| 节点 | 主责 | 必须交付 | 接收方动作 | 通过条件 |
| --- | --- | --- | --- | --- |
| 1. 产品定义 | Product Lead | 确认版产品 Spec：业务问题、目标用户、目标态架构 A、MVP 架构 B、范围、非目标、验收标准、Demo 主线 | Technical Builder 进行技术接手审计 | 关键需求无歧义；验收标准可观察；MVP 与非目标明确 |
| 2. 技术接手审计 | Technical Builder | 可行性结论、复用选项、技术架构、数据与接口需求、工作量、风险及必要的缩减选项 | Product Lead 对范围和取舍作决定 | 不确定项、阻塞和技术边界已显式列出；未默认进入开发 |
| 3. MVP 锁定 | Product Lead 主责，Technical Builder 会签 | 锁定版 MVP Spec 与技术方案；双方确认的范围、验收、工期和风险 | 双方据此进入各自执行范围 | 产品目标与技术承诺一致；不存在未解决的硬阻塞 |
| 4. 开发与验证 | Technical Builder | 可运行实现、技术验证记录、已知限制和风险 | Product Lead 按 Spec 验收产品结果与 Demo 链路 | 核心闭环可运行；模拟能力已标注；验证证据可复核 |
| 5. Demo 收口 | Product Lead | Demo 脚本、展示顺序、限制说明与最终验收记录 | Technical Builder 核对技术事实，总控仅记录状态 | 叙事不夸大能力；现场路径与实际实现一致 |

正常情况下只允许在技术接手审计后往返一次：Technical Builder 提出约束或缩减选项，Product Lead 完成产品取舍，随后共同锁定 MVP。出现新证据、硬阻塞或重大风险时才重新打开已锁定内容。

## 共同边界

- 共同事实源优先级：用户最新决定、根目录 `AGENTS.md`、已确认的 `spec/`、公开一手资料、其他二手资料。
- 联网调研优先使用官方赛事页面、官方文档、原始项目仓库和数据集发布方。
- 不使用 PKFARE 或 Anker 的内部数据，不把模拟能力写成真实能力。
- 未经用户明确授权，不报名、不提交作品、不联系外部人员。
- Product Lead 与 Technical Builder 平级协作，不形成上下级审批链。
- 正式交接必须写入仓库；聊天用于通知和澄清，不作为唯一事实源。

## 总控需要知道的颗粒度

总控 Agent 不是日常任务登记员。Product Lead 与 Technical Builder 对职责内的判断、草稿和普通成果独立负责；只有当总控需要采取动作，或项目方向、状态和风险发生变化时，才即时向上同步。

| 总控需要知道 | 无需即时知道 |
| --- | --- |
| 会改变跨项目目标、共同 Spec、优先级或验收标准的结论 | 产品与技术之间的普通澄清、草稿和局部措辞 |
| 需要用户在互斥方案中拍板的选择 | 职责范围内可独立完成的产品或技术判断 |
| 无法由两线程直接完成的职责冲突或依赖 | 日常排期、常规实现进展和普通提交 |
| 没有替代路径的阻塞、赛事期限或重大风险 | 已有替代路径且不影响里程碑的小问题 |
| 阶段成果已齐备，需要确认是否进入下一阶段 | 尚未达到交接节点的中间成果 |

## 四类向上汇报

两个长期线程只有命中以下一种类型时，才向总控 Agent 发起即时同步。

| 汇报类型 | 触发条件 | 总控动作 |
| --- | --- | --- |
| `请决策` | 存在两个以上互斥方案，选择会改变跨项目目标、范围或验收标准，且超出 Product Lead 的产品取舍权 | 组织用户确认并记录决定 |
| `请协调` | 产品与技术职责冲突，或存在双方都无法直接安排的跨项目依赖 | 明确主责、交付物、顺序和验收标准 |
| `请升级` | 没有替代路径的阻塞；比赛期限受威胁；既有结论失效；出现安全、隐私、许可、授权或真实性风险 | 控制风险、排除阻塞或调整计划 |
| `请验收` | 预先约定的跨项目或治理里程碑已完成，需要记录通过、退回或进入下一阶段 | 对照成功标准检查流程与证据，不代替产品或技术专业验收 |

每次向上汇报只包含六项：汇报类型、一句话结论、触发事实、证据位置、影响范围、总控需要采取的动作。无法归入四类，或总控无需采取动作的，不即时向上同步。

## 跨 Agent 协作

1. Product Lead 与 Technical Builder 以确认版 Spec、技术接手审计和锁定版 MVP Spec 为三个正式交接物。
2. 派单前先从“唯一线程登记”复制接收方线程 ID；不得因线程列表被截断、标题相似或暂时未显示，就 fork 当前线程或新建同名线程。
3. 发起方写清目标、输入、输出、成功标准、允许写入范围和接收方；接收方只对会改变执行方向的缺口发起澄清。
4. 工作树彼此隔离。正式交接物必须先提交到 Git，再用“提交哈希 + 文件路径 + 需要接收方执行的动作”通知对方。未跟踪文件、未提交改动和聊天摘要都不构成交接。
5. 接收方开始工作前必须核对提交哈希和文件路径；看不到交接物时先报告版本或工作树问题，不得基于旧副本继续。
6. 两个线程不在同一文件中并行写入。产品定义归 Product Lead，技术设计与实现归 Technical Builder；双方意见通过引用文件和明确变更项交接。
7. Technical Builder 发现不可行时，不自行删除需求；必须提供约束、证据和至少一个可执行缩减选项，由 Product Lead 做产品取舍。
8. Product Lead 调整产品范围时，不自行承诺技术工期；必须让 Technical Builder 重新确认受影响的工作量与风险。
9. 双方能在既定边界内解决的问题不经过总控。只有职责冲突、跨项目依赖、重大风险或用户级决策才升级。
10. 单次任务内部创建的子 Agent 只属于该线程的临时执行单元，不新增长期角色，也不能替代另一条长期线程。
11. 正式结论必须写入仓库；聊天摘要不能替代产品 Spec、技术方案、验证记录或决策记录。
