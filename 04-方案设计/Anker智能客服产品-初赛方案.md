# Anker 智能客服产品方案

> 初赛方案讨论稿｜2026 年 9 月 23 日
> 赛道四：智能服务——真正听懂，真正解决
> 本文描述产品方案，并区分已验证能力、本轮计划和后续设想。资料来源见[数据源记录](../05-数据资产/2026-09-18-Anker-Demo-数据源链接.md)。

## 1. 要解决什么问题

用户求助时，往往不会按客服系统的字段描述问题。他可能只说“突然不能用了”，发来一张照片，或者先表达对耽误使用的不满。产品名称也可能只是简称。客服如果急着给出标准答案，就可能用错型号的资料；如果每进入一个处理环节都要求用户重新说明，问题虽然被记录了，却没有继续向解决推进。

安克售后服务还涉及产品知识、故障排查、购买渠道和人工处理。一次求助可能跨过几个环节，但用户关心的始终是同一件事：我的问题现在被理解到了什么程度，下一步该怎么做，做完以后是否真的解决了？

### 1.1 业务总览

```mermaid

    A["接住求助<br/>理解诉求与紧迫性"]
    B["确认对象<br/>产品、型号与症状"]

    D["核实服务条件<br/>渠道、凭证与适用规则"]
    E["接续处理<br/>人工介入或售后申请"]
    F["确认结果<br/>解决或继续跟进"]
    A --> B --> C --> D --> E --> F
    classDef stage fill:#EAF2FF,stroke:#4C7EFF,color:#17315C;

```

这是一条业务主线，不要求每位用户走完全部节点。使用咨询可以在获得答案后结束；排障有效可以直接确认解决；安全风险、争议或缺少可靠依据时，应及时交给人工。购买渠道与保修判断是完整售后服务的一部分，但本轮初赛不建设真实订单系统，也不自动批准保修资格。

### 1.2 当前最值得处理的断点

| 断点 | 用户感受到什么 | 产品需要做什么 |
| --- | --- | --- |
| 表达不完整，还带着情绪 | “我已经很着急了，客服却还在重复问基础问题” | 识别用户明确说出的影响和紧迫性，先回应处境，只追问会改变处理路径的信息 |
| 产品和故障线索不清 | 简称相似、照片模糊，收到的步骤却像是针对另一款产品 | 联合文字和可见图片线索形成产品候选；型号未确认前不使用型号专属排障知识 |
| 有答案，没过程 | 用户得到一串链接，不知道先做哪一步，也不知道做完如何继续 | 返回有来源、适用当前产品的一个步骤，记录反馈，再决定下一步 |
| 自助与人工之间断档 | 排障无效后转人工，又要从头讲一遍 | 经用户确认创建工单，带上已确认事实、图片线索、已试步骤和未解决的问题 |

产品的判断标准不是“回复了多少条消息”，而是用户是否拿到了适用的下一步；如果无法自行解决，人工是否能沿着同一份上下文继续处理。

## 2. 产品如何工作

用户始终面对一个售后咨询入口。系统可以在同一段对话里从问题澄清转到知识排障，再转到工单处理；界面会说明当前在做什么，而不是突然切换到另一个聊天框。后台是否拆成多个 Agent，不应成为用户完成服务的负担。本轮采用单 Agent 配合任务流程和工具能力，不为展示“多 Agent”而增加切换。

一次典型的服务按以下方式推进：

1. 用户用文字描述问题，必要时补充一张图片。系统提取产品候选、症状及用户明确表达的使用安排和紧迫性；图片看不清的部分保持未知。
2. 如果产品或症状仍有歧义，系统提出一个会改变后续判断的问题，并让用户确认理解结果。
3. 产品确认后，系统按型号检索适用资料，给出带来源的排障建议。用户每完成一步，可以反馈“已解决”“仍未解决”或补充新的现象。
4. 问题解决时记录结果。知识不足、排障无效或出现安全风险时停止猜测，整理已有信息；需要继续处理的诉求，经用户明确同意后创建工单。
5. 用户看到真实的处理状态：正在检索、等待确认、工单已创建或创建失败。创建工单只表示诉求已受理，不表示故障已解决，也不表示人工已经接手。

情绪理解服务于处理顺序和表达方式，而非给用户贴永久标签。用户明确说“明天就要用”，系统应承认这件事对他的影响，尽快确认产品并给出可执行的检查；如果用户上传的只是设备外观照，系统不能据此断定内部故障。事实判断仍须依靠用户确认和适用资料。

## 3. 产品架构与数据边界

![智能客服产品架构：前端交互页面、Agent 服务应用、工单管理系统与知识库](assets/智能客服产品架构.png)

这张图展示目标产品由前端交互页面、Agent 服务应用、工单管理系统和知识库组成。图中的模块是职责划分，不表示它们已经全部实现。

### 3.1 前端交互页面

产品页面提供售后入口，咨询页面承载文字、单张图片、关键追问、知识来源和排障反馈。方案计划把知识检索、工单处理等后台动作放在同一段对话里，以状态提示和结果卡片告诉用户系统正在做什么。当前原型仍有独立的 S1 Pro 模式，统一入口与可见任务切换是下一步交互改造。

### 3.2 Agent 服务应用

Agent 负责把用户表达转成当前任务所需的信息。模型提取候选产品、症状、反馈和确认意愿；任务流程依据已确认事实决定追问、检索、继续排障或准备交接。知识检索和建单通过工具接口执行，具体操作结果必须回到会话状态中。会话记忆保存已确认产品、已试步骤、用户反馈和工单号，避免下一轮重新开始。

模型可以提出判断，但不能独自越过约束：产品未确认不使用专属步骤；没有可靠知识不编造诊断；建单前必须取得明确同意；接口失败时不能报告成功。后续加入图片和情绪线索，也沿用同样的确认与约束机制。

### 3.3 知识库

知识按产品、故障与排障、保修政策、购买渠道与凭证四类领域组织。每条用于回答的资料应带适用型号和来源。初赛先把少量产品和故障案例做准，再扩内容；遇到相似型号或缺少来源的资料，系统宁可追问或交接，也不能拼出一条看似完整的答案。

本轮多模态的第一步是理解用户上传的图片：识别可见的型号标签、外观或故障线索，再用已确认的产品条件检索文字资料。为图片资料记录产品型号、来源和可见内容，是后续扩案例的基础；直接对图片建立向量索引并做图像相似检索，不是这一阶段的前置条件。

### 3.4 工单管理系统

工单对应一次需要持续处理的服务诉求，不是购买订单。AI 能解决的问题无需建单；自助未解决时，工单保留人工接续所需的上下文。初赛优先定义工单的数据结构与创建规则，不急于建设完整的客服管理后台。

| 数据对象 | 本轮需要保存的内容 | 用途 |
| --- | --- | --- |
| 工单档案 | 工单号、关联会话、已确认产品、问题摘要、创建时间与状态 | 让同一诉求可追踪，避免重复建单 |
| 排障记录 | 建议过的步骤、用户反馈、仍未解决的事项及知识来源 | 人工接手时知道哪些事已经做过 |
| 证据引用 | 用户提供的图片引用及其可见线索；必要时记录购买凭证引用 | 允许人工核对原始材料，不把模型推断当成事实 |
| 操作记录 | 用户建单确认、创建结果及后续状态变化 | 区分“用户同意”“系统提交成功”和“人工开始处理” |

未来若接入真实账号和订单，必须由业务系统核验用户身份及订单归属。当前演示没有安克账号和真实订单接口，不把模拟订单查询写成已具备的能力。客服工作台可以先查看工单和交接摘要；分派、SLA、完整人工对话和自动化规则留待后续设计。

## 4. 方案的重点

第一，系统要听懂当前这次求助。文字、图片和用户明确表达的紧迫性共同帮助它缩小问题范围，但每种线索都有边界。图片能帮助确认可见的产品或异常，不能证明不可见的故障；情绪能影响回应和优先级，不能替代事实核验。

第二，Agent 要把求助推进到可验证的下一步。它保存任务状态，决定什么时候追问、什么时候检索，以及什么时候停止自助。用户反馈会改变后续动作。对用户而言，这是一位持续跟进的客服；对系统而言，模型负责理解和建议，流程与代码负责确认条件和执行边界。

第三，知识回答要能追溯。资料按型号管理，答案附来源，排障按步骤进行。后续可以针对错误召回逐步调整切片、补关键词检索或重排序，但只有在测试集表明现有检索确有缺口时才加入这些机制。资料数量不是本轮的目标，跨型号答错一次，比少收录几款产品更伤害可信度。

第四，自助失败也要留下可用结果。交接摘要使人工能够核对产品、症状、依据和已试步骤；工单状态让用户知道诉求是否真正提交。服务闭环可以是问题解决，也可以是未解决问题被明确、完整地交给下一位处理者，两者不能混为一谈。

## 5. 实现路径与初赛边界

现有原型已经验证了一条文字售后切片：用户用模糊名称描述故障，系统先确认产品，再检索适用的官方资料，逐步排障并记录反馈；无效时在用户同意后创建工单，客服只读页面可以查看交接信息。该案例使用 eufy Robot Vacuum Omni S1 Pro（T2080）吸力变弱问题验证机制，它是测试案例，不是本产品的问题定义或唯一适用场景。实施分支 `codex/anker-s1pro-implementation` 的验收记录显示：186 项自动化测试通过、十类 S1 Pro 样例通过，主链路连续运行三次。结果仅证明这些样例和本地环境，不代表已覆盖安克所有产品。

接下来的初赛增强，优先围绕同一服务链路补齐三件事：单张图片辅助产品确认与可见线索提取；对明确的情绪和紧迫需求作出合适回应；把分散的咨询模式整理成连续、可见进度的用户体验。同时完善工单交接字段，增加少量有来源的产品和图片案例，并用清晰图、模糊图、相似型号图及故障线索不足的案例验证系统何时应追问或停止判断。

| 范围 | 初赛处理方式 |
| --- | --- |
| 必须交付 | 稳定的文字排障与确认后建单链路；方案说明、来源记录、可复现的演示与测试证据 |
| 优先增强 | 单张图片理解、情绪与紧迫性回应、统一会话状态提示、工单交接数据结构和少量补充案例 |
| 视时间决定 | 关键词混合检索、重排序、额外产品覆盖及更完整的客服操作页面 |
| 本轮不承诺 | 真实安克账号和订单绑定、自动判保、维修退换履约、图片向量检索、长期用户画像及多 Agent 协作 |

模型调用或知识检索失败时，系统应保留已确认信息，说明当前无法给出有依据的下一步，并提供重试或人工处理路径。工单创建失败须如实反馈，不得显示“已提交”。这些异常路径与正常排障一起进入演示测试。

### 验证方法

评估按用户最终得到的结果设计，而非只检查回复是否流畅。测试至少覆盖：产品歧义是否被正确追问；图片不清时是否避免猜型号；检索结果是否来自对应产品且能打开来源；用户反馈后是否进入适当的下一步；未获确认是否不会建单；重复确认是否只生成一张工单；失败时是否准确告知状态。现有十类文字样例作为回归基线，新能力使用少量人工核对的图文案例补测。演示时明确标注模拟数据与未接入的业务系统。

### 团队分工与交付

产品与 Agent 负责人负责方案、会话流程、前后端集成、工单数据模型与整体演示，对闭环结果负责。知识资料的收集、来源核对和测试案例可由队友协作；资料协作延迟时，先使用已验证的官方资料完成主链路，不让内容扩张阻塞交付。
