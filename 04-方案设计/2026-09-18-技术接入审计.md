## 缺失的正式产品输入

在开始技术设计或实现前，Product Lead 需要写入并标明已确认的：

1. 单一 Demo 故事线：用户起点、触发变化、完成结果。
2. MVP 用户流程与每步验收标准：何时追问、何时调用工具、何时需要确认、何时算解决。
3. 工具范围与真实性：知识库、订单、售后、工单中哪些为模拟；每项输入、输出、失败情况与风险等级。
4. 目标界面与演示方式：Web 对话界面、命令行或其他；工具轨迹与确认信息如何展示。
5. 演示数据与评估用例：产品资料、订单样例、故障/售后规则、至少一条正常与一条异常路径。

## 主要风险

| 风险 | 影响 | 缓解/缩减方向 |
| --- | --- | --- |
| 产品故事线未定 | 无法定义工具、数据和验收，易造成返工 | 等正式 MVP 交接后再编码 |
| 真实服务系统不可接入 | 无法宣称真实订单、售后或工单能力 | 使用可追溯的模拟数据与 mock 工具，并在 UI/Demo 中标注 |
| 工具调用不稳定或模型偏航 | 关键动作可能不透明或越权 | 强制 schema 校验、规则拦截、确认闸门、预设演示数据 |
| 时间窗口短 | 过早引入多 Agent、向量库、登录和真实第三方集成会挤压可演示闭环 | 保持单 Agent + 三个以内 mock 工具 + 两条高质量路径 |
| 评估资产缺失 | 不能证明追问效率、确认控制或异常恢复有效 | 先创建小型黄金测试集，覆盖正常、信息缺失、工具失败/异常三类情况 |

## 收到正式 MVP 后的建议实现顺序

1. 将正式流程转为状态机、工具契约和验收用例；以一条完整故事线评审通过为准。
2. 建立演示数据与 mock 工具（知识、订单、售后/工单）；逐个验证输入、输出与失败分支。
3. 实现单 Agent 编排与规则/确认闸门；验证不可越过高风险确认。
4. 实现最小界面与会话、工具轨迹、解决状态展示；验证用户能看见依据、动作和控制点。
5. 加入异常恢复与基础测试集；至少跑通正常、关键追问、工具失败/变更三条路径。
6. 用固定脚本彩排 Demo，并将模拟边界、已知限制和测试结果写入交付材料。
