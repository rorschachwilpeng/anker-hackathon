## 2. 本轮交付范围

### 2.1 本轮执行

1. 迁入队友浅紫配色、留白、图标导航、欢迎区、卡片、消息和输入区的视觉设计。
2. 首页保留“你好”，以三张卡片与同名侧栏入口对应：订单与物流、产品咨询与排障、售后跟进。
3. 连接既有通用客服、单图排障、订单详情、建单及工单读取能力。保留流式回复、工具状态、知识来源、确认建单、停止和错误提示。
4. 分离导航切换与新建会话，防止换模块或返回首页时丢失当前记录。
5. “售后跟进”先读取现有工单接口的实际字段，支持查看当前工单和刷新已有状态；通过已知工单号或用户输入的工单号定位，不展示所有用户工单列表。
6. 统一订单详情页、工单工作台的基本配色、字体和按钮样式，保留原功能；客服工作台在独立标签页打开。
7. 在技术交付记录中逐项列出三个 Demo 的已有支持、此次新增、仍未完成及未验收内容。

### 2.2 单列的业务缺口

以下属于初赛方案的完整目标，但不能把它们的完成情况归入“换前端已完成”：

- 人工回复写入与对话内读取、用户处理结果反馈写入。
- Agent 自然语言查询工单最新进度、转达人工回复。
- “待处理 → 处理中 → 已处理”的完整状态流转与用户解决反馈衔接；当前工作台使用“已解决”，与目标术语不同，需要连同接口校验、存储一起评估。
- 通用客服与单图排障之间跨处理链路迁移任务状态、任意业务跨模块连续处理。
- 对最新 Demo 情绪响应要求与现有流程的差异进行核对。

Builder 先判断是否已有可复用能力；确属未实现的部分，给出最小实现范围、相关文件和技术约束，单独回传，不擅自扩大本轮后端开发。缺口不阻止先完成可独立交付的界面合并；缺口存在时不得宣布完整 Demo 已通过。

本轮不新增登录、多用户权限、历史会话中心、真实安克系统接入、退款或订单修改能力，不向 main 合并，不改变队友仓库或公开站点部署。

### 3.1 首页及侧栏

| 位置 | 显示内容 | 点击行为 |

| 主按钮 | 新对话 | 明确开始新的服务会话，清除页面当前会话绑定；保留数据库已有记录 |
| 首页卡片与侧栏 | 订单与物流 | 同一目标视图，同步标题与侧栏选中项 |
| 首页卡片与侧栏 | 产品咨询与排障 | 同一目标视图，同步标题与侧栏选中项 |
| 首页卡片与侧栏 | 售后跟进 | 同一目标视图，优先读取当前会话已建立的工单 |
| 侧栏底部 | 客服工作台 | 在独立标签页打开现有 /s1pro/workbench |
| 侧栏底部 | 关于演示 | 说明支持范围、模拟数据与实际能力；其中提供内部“售后信息提取”入口，保留现有提取功能 |

首页文案：标题“你好”，说明“有什么可以帮你？”。卡片说明：

- 订单与物流：查看订单信息和配送进度。
- 产品咨询与排障：了解产品用法，解决使用问题。
- 售后跟进：查看工单进度与处理记录。

首页及空会话模块视图可选择示例问题；点击只填入输入框，不自动发送或推进预录步骤。输入内容可以修改。用户也能直接输入问题。

全局保持现有服务可用性提示；运行系统不再显示“演示回放”或“回复为预录内容”。订单和工单仍须准确标注演示数据/本地演示，不暗示已接入安克客服。

### 3.2 模块内容

**订单与物流**

- 示例：“我买的 S1 Pro 还没收到，帮我查一下。”
- 不提前绑定 DEMO-1001；由 Agent 追问，用户输入后才查询。
- 展示既有订单卡片，详情从卡片打开；后续“那明天能收到吗？”“收到以后，这台 S1 Pro 第一次怎么用？”继续原会话。
- 已知订单里的型号由服务端作为后续检索依据；前端不猜测型号或预计送达日期。

**产品咨询与排障**

- 示例一：“我的 S1 Pro 最近吸力变弱了，怎么办？”——对应同名产品澄清。
- 示例二：“我的 S1 Pro 扫地机器人吸力变弱了。”——对应排障与人工接续。
- 进入视图不代表已确认品类或型号。页面可说明演示支持范围，但不得把入口、示例标签或演示说明写成“已确认产品”。
- 保留 JPG/PNG 单图上传、预览、移除、拖放、大小与格式反馈、发送后图片展示。
- 模型输出与真实状态驱动产品确认、排障步骤、官方来源、操作反馈和建单确认。
- 用户在原对话中表达无效、不满或要求转人工时，延续既有流程；不要求用户换模块或重新描述问题。
- 可保留“需要人工协助”按钮，但它只是明确表达转人工意愿，仍需核对交接内容和确认建单；不能直接创建工单。

**售后跟进**

- 有当前工单：读取 /s1pro/tickets/{ticket_no}，显示工单号、实际状态、问题和已保存的处理/交接信息。
- 无当前工单：显示“当前会话还没有工单”，提供输入已知演示工单号的入口，以及返回产品咨询的入口。不自动建单。
- 显式“刷新进度”重新读取服务端数据；切入此视图也重新读取。读取失败不把旧状态显示为最新结果。
- 用户已确认的工单号和服务会话保持绑定；仅切换视图不丢失绑定。明确新对话后不自动带入上一会话工单。
- 本轮不显示虚构人工回复，不提供尚未接通的回复/反馈提交按钮。既有字段与完整 Demo 缺口在技术记录中说明。
- 本轮不伪造统一状态：展示接口实际返回值；状态枚举统一属于第 2.2 节待评估项。
- 对话内自然语言查询工单不能假定已实现，须在缺口清单明确状态；页面读取不算 Agent 已具备查询能力。

## 4. 会话连续性与接口边界

### 4.1 必须分开的操作

| 操作 | 会话与数据处理 |
| --- | --- |
| 首页卡片、侧栏切换、返回首页 | 只改变展示视图和导航选中项，保留当前 conversation_id、消息、订单/产品/工单上下文及输入草稿 |
| 同一会话继续追问 | 使用兼容的既有服务链路和同一会话；不重复提交历史消息制造新会话 |
| 排障中转人工、查看当前工单 | 沿用原服务记录；展示既有建单确认和工单返回 |
| 新对话 | 重置前端会话与任务绑定，不删除数据库记录；各 Demo 从这里独立开始 |
| 请求进行中 | 沿用现有禁止切换/重复发送策略，避免请求结果写入错误视图；停止按钮仍可用 |
| 图片草稿切换视图 | 保留在原输入上下文；不会误发到不支持图片的接口 |

当前 chat.js 的 reset(next) 同时改 mode、清 conversationId 和消息；此逻辑不能直接用作新侧栏的导航事件。

UI 模块不能直接等同于后端 mode。案例一查订单后继续问产品用法，应继续复用 /chat 的订单上下文能力；案例二与案例三的排障、确认建单在原 /s1pro/chat 链路内继续。

Builder 在接手审计中确认 /chat 和 /s1pro/chat 的会话与任务状态兼容性。不得未经核对，仅因两者参数都叫 conversation_id 就跨接口复用。跨链路迁移若需要后端改造，列入缺口；先保留活跃服务链路和记录，不在导航点击时偷偷重置或错接请求。说明未支持的操作，不能以静态提示假装已迁移。

首页直接输入复用现有通用客服能力。本轮不宣称已提供任意输入在所有业务链路间自动路由的统一 Agent。

### 4.2 既有接口与事件

| 用途 | 现有接口/协议 |
| --- | --- |
| 通用客服 | POST /chat；JSON message、conversation_id |
| 单图排障文字轮次 | POST /s1pro/chat；JSON message、conversation_id |
| 图片轮次 | POST /s1pro/chat/image；multipart message、conversation_id、image |
| 订单读取与详情 | GET /api/orders/{order_no}；GET /orders/{order_no} |
| 工单读取与工作台 | GET /s1pro/tickets/{ticket_no}；GET /s1pro/workbench |
| 工作台状态更新 | POST /s1pro/tickets/{ticket_no}/status；沿用服务端实际契约 |
| 内部提取工具 | POST /after-sales/extract |
| 服务连通状态 | GET /health |

通用 SSE 保留 session、answer_reset、tool_status、order_card、knowledge_sources、token、error、done；单图排障文字轮次保留 stage、search_done、result、error，并保留图片轮次 JSON 返回处理。现有停止、超时、重新编辑与已提交工单提示不得随视觉迁移丢失。

## 7. Demo 对照与交付口径

### 案例一：订单查询与知识分域

依次输入：
1. “我买的 S1 Pro 还没收到，帮我查一下。”
2. “订单号是 DEMO-1001。”
3. “那明天能收到吗？”
4. “收到以后，这台 S1 Pro 第一次怎么用？”

要求：缺号追问；实际接口返回订单卡片和同源详情；空预计送达时间不猜测；首次使用回答沿用订单中的 T2080，展示官方来源且不引用 T8D04。全程不要求换模块或重新提供已知型号。

### 案例二：同名产品澄清与图片排障

依次操作：
1. “我的 S1 Pro 最近吸力变弱了，怎么办？”
2. 等待品类澄清，上传可读出 T2080 的铭牌照片，并输入“是扫地机器人，就是这台。”
3. 获得对应官方排障建议。
4. “我按你说的步骤试过了，现在吸力恢复正常了。”

要求：确认前不写入 T2080、不提供型号专属建议；图片只提供可见线索；展示实际型号及来源；记录解决反馈，不建单。前端不得通过默认选择产品绕过澄清。

### 案例三：排障无效后人工接续

1. “我的 S1 Pro 扫地机器人吸力变弱了。”
2. “我按你说的做了，还是没用，已经折腾很久了，你们到底能不能解决？”
3. “摘要没问题，可以建单，帮我转人工。”
4. 客服打开工单并标记处理中。
5. “我的工单现在处理到哪一步了？”
6. 客服填写进一步处理意见。
7. “人工有回复了吗？我接下来要怎么做？”
8. “我按客服补充的建议处理好了，现在能正常用了。”
9. 客服确认后标记已处理；用户询问“现在工单是什么状态？”

最新飞书要求：在第 2 步回应用户不满并主动建议转人工，不再机械追加排障步骤；摘要包括用户自述的着急原因（若提供）、问题、已尝试步骤、反馈和来源；人工回复本身不触发结单。
