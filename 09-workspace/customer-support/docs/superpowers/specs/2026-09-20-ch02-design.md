# 第 2 章设计提案：在客服聊天中接入单轮工具调用

状态：2026-09-20 用户以“上边的两个改动都符合我的需求，进行修改”确认设计与 DDL；进入实施计划阶段，产品代码尚未实施。

## 目标与固定边界

沿用现有聊天页面、FastAPI、LangChain 和 .env 模型配置。新增 SQLAlchemy + Docker MySQL。用户在聊天页提问即可触发模型自主选择工具，SSE 输出工具状态和最终回答，保存消息及工具轨迹。不增加 Agent Loop、向量检索、RAG 或真实订单接口。

## 方案比较与推荐

1. 推荐：数据库作为会话历史来源，聊天服务显式执行一次工具选择和一次结果收敛。客户端传 conversation_id，分层清晰，工具消息能完整回放。
2. 保留前端 history，数据库仅留副本：改动少，但双份历史容易不一致，客户端也无法可靠表达工具轨迹，不推荐。
3. 引入 Agent 执行器再限制步数：本章不需要，且违背不做 Agent Loop 的范围，排除。

## 分层及表结构

路由负责参数和 SSE；聊天服务负责编排；工具注册表和执行器负责白名单、校验、超时重试；仓储负责 SQLAlchemy 查询和事务；数据库模块管理引擎与会话工厂。不让慢模型请求持有数据库事务。

表结构严格以用户提供的 `ecommerce-support/sql/ch02-schema.sql` 为准，仅建四张业务表，不自行添加列：

- faq：id、question、answer、category、created_at、updated_at。
- conversations：id、user_id、status、created_at、updated_at；status 为进行中/已转人工/已结束。
- messages：id、conversation_id、role（user/assistant/tool）、可空 content、tool_calls JSON、tool_call_id、created_at。工具申请属于 assistant 行，结果属于 tool 行，不增加完成状态列。
- tickets：ticket_no 主键、conversation_id、description、ticket_type（售后/投诉/咨询）、status（待处理/已处理）、created_at。不增加幂等键列，以同一工具调用复用的 ticket_no 主键去重。

保留 DDL 的 UNSIGNED BIGINT、字段长度、枚举、外键、索引、默认值和更新时间行为；统一 InnoDB/utf8mb4。SQLAlchemy 映射必须与该 DDL 一致。原始建表 SQL 适用于空库，不宣称其 CREATE TABLE 可重复执行；初始化入口负责检测现有结构并拒绝不兼容结构，不删除重建。

初始化脚本可重复执行，灌入 FAQ 和一组明确标注的演示会话、消息、工单，不清空既有数据。订单、商品、物流不建表，仅工具内部随机生成一致的演示结果，并在结果及回答中标明模拟数据。

## 会话接口与上下文

POST /chat 使用 message、可选 conversation_id；首次创建会话，通过 SSE session 帧返回 id，后续请求由服务端加载消息。现有页面和 curl 示例同步更新。旧 history 字段迁移在实施计划中明确处理，不悄悄忽略用户传入历史。

本章为本机单用户演示，user_id 由服务端使用演示身份，不伪称已实现登录鉴权。新聊天创建新会话；刷新恢复、历史会话列表不在本章范围。同会话并发请求明确拒绝，避免交错写入。

历史按完整用户轮次裁剪，工具申请与其结果成组保留。预算覆盖系统提示、工具定义、调用参数、结果及输出预留；工具返回限制体积。数据库保留流水，模型只读取完整可回放轮次。

## 单轮编排（提议：最多实际执行一个工具）

1. 校验请求，保存 user 消息；模型绑定五个工具，自动决定直接回答还是调用工具。
2. 无工具时直接流式返回回答。有工具时汇总完整参数后校验，不执行残缺参数；保存 assistant 工具申请，推送工具状态。
3. 最多执行一个工具并保存对应 ToolMessage。若模型申请多个工具，只执行第一个，其余回灌明确的本轮限制错误，保持每个调用 id 都有配对结果。
4. 用不开放工具调用的模型请求流式生成最终回答；最多两次模型请求，不自动再次规划或调用工具。
5. 最终答复成功落库后发送 done。只有完整生成的最终正文写入 assistant 行，不将半截正文冒充完整回答；流错误及中断原因写运行日志，工具错误写对应 tool 消息。按 user 消息划分轮次，缺少最终 assistant 正文或工具配对不全的轮次不回放。现有 DDL 无独立完成状态列，因此无法仅凭 messages 区分中断与上游错误，不能宣称支持该能力。已提交工单不因生成中断而撤销。

SSE 保留 token/done/error，增加 session 和 tool_status。工具状态包含工具名、调用 id、运行/成功/失败/重试状态；前端气泡徽章随帧更新。页面改造按用户明确要求直接迭代。

## 五个工具及错误处理

- query_order(order_id)、query_product(product_id)、query_logistics(order_id)：内部生成随机演示数据。
- query_faq(keyword)：参数化 SQL LIKE 查询问题列，转义 LIKE 通配符，限制返回条数；无命中返回显式 not_found。
- create_ticket(description, ticket_type)：会话 id 从服务端执行上下文注入，不由模型指定。服务端为同一工具申请分配固定工单号，所有内部重试复用它。创建工单和将会话设为“已转人工”在同一事务提交。

所有工具均用 LangChain @tool 和参数 Schema，注册表拒绝未知工具。超时及暂时性故障最多重试一次；参数错误、未知工具、FAQ 无命中不重试。工单重试使用相同 ticket_no；遇主键冲突时核对既有行的会话、描述和类型，一致才视为同一操作成功，不覆盖已有行。该约束保证同一次工具执行的内部重试去重，不宣称不同 HTTP 请求自动去重。异常结果回灌模型，不泄露数据库或密钥信息。

## FAQ 漏召回与验证

种子 FAQ 包含“退货政策”和“运费标准”，问题列不包含“邮费”。关键词提取提示要求保留原词，不做同义词扩展；“退货政策是什么”提取“退货政策”，“邮费是多少”提取“邮费”。SQL LIKE 原样查问题列，后者应无命中；不添加仅针对验收句子的硬编码拦截，也不让模型凭常识编造商家运费。

通过真实样例记录模型选择的工具、参数、返回条数和最终回答。漏召回按预期结果验收，留下下一章 RAG 升级依据。如果模型自行改写关键词导致命中，应明确记录为不满足该验收，调整提示后重新评估。
