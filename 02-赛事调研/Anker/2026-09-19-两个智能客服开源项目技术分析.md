# 两个智能客服开源项目技术分析

> 调研对象：[`Shaurya856/Customer_Support_Agent`](https://github.com/Shaurya856/Customer_Support_Agent) 与 [`abdullahahsen05/supportflow-ai`](https://github.com/abdullahahsen05/supportflow-ai)  
> 调研日期：2026-09-19  
> 调研方法：交叉核对 README、目录结构和关键源码。本文区分“README 宣称”“源码已实现”和“未发现实现”，不把路线图视为现有能力。

## 1. 结论摘要

两个项目代表两种不同的实现路线：

- **Customer Support Agent** 是一个较小但 Agent 特征更明确的演示：LLM 原生决定是否调用工具，LangGraph 负责 Agent 与工具之间的循环，并实现了会话 checkpoint、长期用户记忆和代码级确认门禁。它适合参考 Agent 核心闭环，但订单、工单和人工升级都是本地模拟。
- **SupportFlow AI** 更接近一套完整客服产品原型：包括消费者聊天页、FastAPI 服务、RAG、PostgreSQL、工单后台、反馈和 MLflow 记录。不过它的意图分类主要依靠正则规则，工具由程序直接分派，并非 LLM 原生 Function Calling；会话虽然落库，但历史消息尚未真正参与下一轮推理。

对 Anker 售后智能客服而言，最合适的组合不是照搬其中一个项目，而是：采用第一个项目的 **Agent 循环、双层 Memory 与确认门禁**，结合第二个项目的 **RAG、结构化数据、工单后台与可观测性**，再补上两个项目都缺少的 **产品消歧、多模态故障理解、面向售后排障的状态设计和严格权限校验**。

## 2. 项目一：Customer Support Agent

### 2.1 定位与技术栈

这是一个语音外壳之下的 LangGraph 客服 Agent，界面为 CLI，主要处理模拟订单查询、创建支持工单和人工升级。

| 层面 | 源码实现 |
| --- | --- |
| LLM | Groq OpenAI-compatible API，`llama-3.3-70b-versatile` |
| Agent 编排 | LangGraph，两类节点：`support_agent` 与 `tools` |
| Function Calling | LangChain `bind_tools`，共 6 个工具 |
| 短期状态 | LangGraph `SqliteSaver` checkpoint |
| 长期记忆 | 每个手机号一份文本文件 |
| 语音 | Parakeet/Whisper STT，Edge TTS |
| 界面与服务 | CLI；未发现 Web 前端或 API 服务 |

README 将主模型描述为 NVIDIA NIM，但当前 `customer_support_agent/nodes.py` 实际启用的是 Groq，NVIDIA 代码已经被注释。因此应以源码为准。

### 2.2 整体架构与一次请求链路

1. `customer_support_agent/main.py` 读取用户手机号，并加载对应长期记忆。
2. 用户选择创建新问题，或继续一条未解决且未升级的旧会话。
3. 同一个 `session_id` 被用作 LangGraph `thread_id`，`SqliteSaver` 恢复该会话的消息和状态。
4. `support_agent` 将长期记忆注入系统提示词，由 LLM 回复或产生工具调用。
5. 如果产生工具调用，图路由到 `tools_node`；工具结果以 `ToolMessage` 返回，再交给 LLM 组织最终回复。
6. 会话结束、超时或升级时，将问题、处理步骤、工单号和结果写回长期记忆。

这里的 LangGraph 很轻，只负责控制“LLM → 工具 → LLM”的循环。它没有按订单、退款、投诉等业务意图拆多个图节点；业务判断主要写在 `customer_support_agent/memory.py` 生成的系统提示词中。

### 2.3 Function Calling、约束与 Memory

`customer_support_agent/tools.py` 定义了 6 个工具：查询用户订单、查询订单详情、创建工单、人工升级、编辑记忆和保存会话。`customer_support_agent/nodes.py` 使用 `bind_tools` 让 LLM 原生选择工具，并额外修复模型偶尔将工具调用输出成文本标签的问题。

项目最值得借鉴的是两项机制：

- **代码级确认门禁：** 创建工单或升级人工前，`tools_node` 会检查用户是否明确确认；没有确认就阻断调用，而不是只依靠提示词约束。
- **两层 Memory：** SQLite checkpoint 保存单次会话的完整运行状态；手机号文本文件保存跨会话的用户偏好、历史问题、是否解决、处理步骤与工单号。

但确认判断目前较宽松，只要最近一句话出现 `yes`、`ok`、`please` 等词就可能被视为确认；长期记忆也会整体拼进提示词，尚无摘要压缩、长度控制或敏感信息治理。

### 2.4 RAG、工单、人工升级与评估

- **RAG：未发现。** 项目没有文档解析、向量索引、检索器或知识来源引用；硬编码订单查询属于业务工具，不是 RAG。
- **工单：仅为模拟。** `create_ticket` 写入进程内 `TICKETS` 字典，服务重启后数据丢失。
- **人工升级：仅为状态模拟。** `escalate` 生成一段升级文本并保存状态，没有人工队列、客服工作台、通知机制或真实接管流程。
- **评估：存在单元测试，但未发现系统化 Agent Eval。** 测试覆盖工具、确认门禁、记忆、路由和语音处理；未发现问题解决率、检索质量、端到端对话集或人工交接质量评估。
- **可观测性：较弱。** 只有控制台耗时、日志和会话步骤，未发现 trace、指标、告警或仪表盘。

此外，`get_order_details(order_id)` 没有校验订单是否属于当前手机号，存在跨用户读取风险；仓库中还发现一处公开硬编码的第三方访问凭据。两者都说明该项目只能作为架构参考，不能直接作为生产底座。

## 3. 项目二：SupportFlow AI

### 3.1 定位与技术栈

这是一个本地运行的客服平台原型，产品形态比项目一完整：消费者聊天页、客服管理后台、后端 API、RAG、业务数据库、工单、反馈和运行记录都在同一仓库内。

| 层面 | 源码实现 |
| --- | --- |
| 前端 | Next.js 15、React、TypeScript、Tailwind CSS |
| 后端 | FastAPI、Pydantic、SQLAlchemy、Alembic |
| LLM 与 Embedding | Ollama：Mistral 7B、nomic-embed-text |
| Agent 编排 | LangGraph 四节点工作流 |
| 知识检索 | ChromaDB + Markdown 知识文档 |
| 业务数据 | PostgreSQL |
| 工单 | PostgreSQL 工单表、REST API、后台页面 |
| 可观测性 | MLflow 记录每次聊天运行 |

### 3.2 整体架构与一次请求链路

1. Next.js 聊天页把当前消息、`conversation_id` 和演示用户邮箱发送到 `POST /api/chat`。
2. `backend/app/api/chat.py` 获取或创建会话，并先保存用户消息。
3. LangGraph 从 `classify` 节点开始，根据正则和关键词识别意图、情绪并抽取订单号或邮箱。
4. FAQ/未知问题进入 RAG；订单、退款、订阅、账单和人工升级进入工具节点；缺少关键参数时直接返回追问。
5. RAG 或工具结果被组装为上下文，再由 LLM 生成回答；没有真实工单时，代码会清除可能幻觉出来的工单号。
6. API 保存 AI 回复、工具调用、工单关联、意图与情绪，并把运行参数、耗时、来源、工具结果和错误写入 MLflow。

核心图定义在 `backend/app/agent/graph.py`，只有 `classify → retrieve/run_tool → generate_answer` 三类路径。它是确定性工作流，不是可以循环追问、持续调整计划的 Agent loop。

### 3.3 Workflow 与工具调用的真实边界

README 使用了“tool-calling”和“关键词 + LLM fallback”这两种说法，但源码既没有模型原生 Function Calling，也没有意图分类的 LLM fallback。`backend/app/agent/nodes.py` 先用正则分类意图，再在 `run_tool_node` 中通过 `if/elif` 直接调用 Python 函数；LLM 只负责根据已有上下文生成最终回答。代码中的置信度也是固定值，尚未用于路由或升级决策。

这种方式的优点是路径清楚、便于测试，适合固定意图的演示；缺点是新场景必须继续添加正则、参数抽取和分支，面对 Anker 场景中“产品不明确、症状含糊、排障后继续反馈”的多轮问题时扩展性较差。

项目定义了 7 个 PostgreSQL 业务函数，包括订单、用户、订阅、支付、退款资格、创建工单和人工升级，但 Agent 图实际接入 6 个，`get_user_profile` 未进入当前路由。工具返回 Pydantic 结构，边界比项目一清晰，但聊天接口以用户提交的邮箱作为身份，未发现真实登录、鉴权或数据归属校验；更严重的是，前端传入的 `user_email` 没有交给 `run_agent`，重复扣款场景缺少邮箱时还会使用硬编码演示账户。因此该身份链路不能直接用于生产环境。

### 3.4 Memory、RAG、工单与评估

**Memory / 状态。** PostgreSQL 保存 conversation、message、tool call、ticket 等记录，前端也持续传递 `conversation_id`。但 `run_agent(message)` 每轮只接收当前一句消息，未从数据库加载历史消息，也未使用 LangGraph checkpointer。因此目前是“会话记录已持久化”，还不是“历史上下文参与推理”的多轮 Memory。

**RAG。** `backend/app/rag/ingest.py` 把 Markdown 文档按 800 字符、100 字符重叠进行切分，用 Ollama embedding 写入 ChromaDB；`retriever.py` 默认返回 top 4，并带回标题、文件路径和距离。来源回传已实现，但未发现产品型号元数据过滤、相关性阈值、重排、冲突知识处理或检索效果评估。API 请求虽然带有可配置的 `k`，当前实现并未传入 Agent，检索节点仍固定使用 4；未知问题也会进入向量检索，因此“没有答案时诚实拒答”并非确定性保证。

**工单与人工接管。** 工单真实写入 PostgreSQL，包含状态、优先级、类别、摘要、升级原因、负责人和关联会话。后端支持列表、详情与更新，前端有客服后台和工单详情页。它已经具备“记录与查看”的骨架，但未发现自动分派队列、SLA、通知、接管聊天、内部备注或规则配置中心。

**评估与可观测性。** MLflow 已落地，记录模型、意图、工具、延迟、置信度、来源数、工单和错误，并保存消息、回答、来源和工具结果。不过一次请求发生多个业务动作时只记录主工具，例如查支付后自动升级，第二次动作不会作为独立 tool call 入库。README 架构图中的“Quality Check”也不是独立节点，源码只用正则删除没有真实工单时被模型虚构的工单号。DeepEval、Prometheus 和 Grafana 仍属于未完成路线图，不能视为已实现。

## 4. 两个项目的差异

| 维度 | Customer Support Agent | SupportFlow AI |
| --- | --- | --- |
| 产品形态 | CLI/语音 Agent Demo | 前后端与客服后台组成的平台原型 |
| Workflow | LLM 决策工具，LangGraph 循环 | 规则分类后走固定单程图 |
| Function Calling | 已实现原生 `bind_tools` | 未实现原生 Function Calling，程序直接分派函数 |
| 多轮状态 | SQLite checkpoint 可恢复 | 记录落库，但未回灌 Agent 推理 |
| 长期记忆 | 手机号文本文件 | 会话、消息和工具记录数据库 |
| RAG | 未发现 | ChromaDB RAG 已实现 |
| 工单 | 内存字典，重启丢失 | PostgreSQL + API + 管理后台 |
| 人工升级 | 仅生成升级状态 | 创建升级工单，但未实现实时接管 |
| 操作前确认 | 创建工单/升级有代码门禁 | 自动建单/升级，未发现用户确认门禁 |
| 可观测性 | 控制台日志与计时 | MLflow 运行记录 |
| 主要价值 | Agent 核心闭环与 Memory | 平台组件、RAG、工单与运营后台 |

## 5. 对 Anker 售后智能客服的可迁移设计

### 5.1 建议直接借鉴

1. **从项目一借鉴 Agent 主循环。** 让 LLM 负责理解产品、症状和用户反馈，Workflow 管理追问、检索、排障、确认和升级，而不是为每一种自然语言写大量正则。
2. **从项目一借鉴双层 Memory。** 区分当前任务状态与跨轮服务记录，但长期信息应存结构化数据库，不采用自由文本文件。
3. **从项目一借鉴代码级确认。** 创建工单、提交申请、修改用户资料等有副作用的操作必须在工具执行层验证确认状态。
4. **从项目二借鉴 RAG 管线。** 保留文档来源、产品型号、知识域、地区、版本和生效时间，并在检索时做元数据过滤。
5. **从项目二借鉴工单与运营后台。** 对话、工具调用、诊断步骤和工单建立关联，人工可看到 AI 已确认的信息和未解决事项。
6. **从项目二借鉴运行记录。** 至少记录意图、产品候选、检索来源、工具输入输出、用户确认、转人工原因、延迟与结果。

### 5.2 不能直接照搬

- 两个项目都没有 Anker 赛题需要的故障图片理解、产品外观/型号消歧和多模态证据整合。
- 项目一没有知识库，项目二的知识库是通用政策文档，均没有围绕“产品知识—故障症状—诊断问题—排障步骤—停止自助条件”组织内容。
- 项目一的工单与人工升级是 mock；项目二虽然有工单后台，但没有真正的客服接管和自动化规则配置。
- 项目一把较多业务约束放进 prompt，项目二把较多意图写死在正则中。Anker 方案应把安全、权限、确认和工单规则放到确定性约束层，把含糊理解和对话生成交给 LLM。
- 两个项目的身份与数据权限都不足，不能直接连接真实订单、保修或用户资料。

## 6. 后续系统流程图建议

后续要画的不是传统 User Flow，而应是一张“单次服务中各组件如何协作”的系统流程图。建议用下面这条主线作为图的文字底稿：

> 用户提交文本/图片 → API 加载会话状态与关联工单 → LLM 形成结构化理解（产品候选、症状、意图、待确认信息）→ Constraint 校验是否需要追问或停止自助 → Workflow 决定检索知识或调用工单工具 → RAG 返回带产品、版本和来源的证据 / 工单系统返回真实执行结果 → LLM 组织下一步指导 → Memory 保存已确认事实、已做步骤和用户反馈 → 若无法闭环，取得用户确认后创建工单并携带摘要交给人工 → 记录运行轨迹并进入评估。

这张图中需要把三类关系画清楚：

- **LLM 负责理解与生成，Workflow 负责控制步骤，Constraint 负责硬边界。**
- **Function Calling 是 Agent 访问知识库和工单系统的接口机制，不等于业务流程本身。**
- **Memory 保存服务状态；工单保存需要持续跟进的业务对象；两者不可合并。**

## 7. MVP 技术方案建议

初赛聚焦售后咨询和排障，不必先实现订单系统。一个可演示且范围受控的 MVP 可以包括：

| 组件 | MVP 范围 |
| --- | --- |
| 前端交互 | 文本、单张故障图片、产品确认、分步排障反馈、知识来源与工单状态 |
| Agent | LLM、LangGraph Workflow、Function Calling、会话 Memory、代码级 Constraint |
| 知识库 | 产品知识、故障与排障知识、保修售后政策、购买渠道与凭证知识 |
| 工单系统 | 工单创建、补充处理记录、状态查询、人工工作台列表与详情 |
| 工具函数 | `search_knowledge`、`get_ticket`、`create_ticket`、`append_ticket_record` |
| 运行记录 | 每轮输入输出、结构化理解、检索来源、工具调用、确认与升级原因 |
| 最小评估 | 产品识别、排障依据、工具调用正确性、越权/未确认操作、人工交接完整性 |

建议演示主线仍聚焦一个具体产品故障，例如 S1 Pro 吸力下降：先完成产品消歧，再根据知识库逐步排障；用户反馈无效后，Agent 汇总型号、症状、图片线索、已尝试步骤和知识来源，经确认创建工单。这样能同时证明 LLM 理解、Workflow、RAG、Memory、Constraint、Function Calling 和工单交接，而无需在初赛阶段引入完整订单与履约系统。
