# Anker 智能服务 Agent 调研地图

> 状态：阶段调研，供 MVP 与 Demo 选型使用，不构成 Anker 内部流程或数据的描述。  
> 调研日期：2026-09-17（Asia/Shanghai）。  
> 证据规则：`事实`均链接到第一方文档、代码仓库或数据集主页；`推断`是基于这些事实的设计判断；`建议`是本项目的取舍。未核验的能力不作为 Demo 承诺。

## 0. 结论先行

**建议做一个单 Agent、三个只读工具、一个受控写入工具的“设备问题解决闭环”，而非普通 FAQ 聊天机器人。**

推荐故事线：用户报告“充电宝无法充电/充不进电”，Agent 只追问会改变诊断或售后路径的两项信息（型号、现象/安全征兆），展示命中的知识依据，执行模拟订单查询与资格检查；在创建售后申请前展示影响、风险和将写入的内容，等待用户确认。最后询问问题是否解决；未解决或出现鼓包、异味、过热等高风险信号时转人工。

这是对共同内核的场景化：把“该问、该答、该规划、该行动、该确认”的判断显式呈现在时间线中。订单、退款、退换或工单创建均为**模拟系统**，界面须清楚标注。

## 1. 调研地图：要验证什么

| 问题 | 可验证的最小能力 | 成功证据 | 不做什么 |
| --- | --- | --- | --- |
| 知识是否可靠 | 产品/故障问答附来源片段和适用条件 | 回答可打开到对应知识条目；无证据则不编造 | 把实时订单和库存塞进向量库 |
| 是否少问关键问题 | 仅在型号、症状或订单归属会改变下一步时提问 | 3 个脚本中每次追问可解释“它改变什么” | 机械表单式盘问 |
| 是否能处理服务动作 | 订单查询、资格判断、创建售后申请被拆成工具 | 工具卡展示输入、返回、状态和模拟标识 | 模型文字直接承诺退款/换货 |
| 用户是否仍有控制权 | 高影响动作有预览、确认/取消和替代方案 | 未确认时不产生写入；取消后仍给人工渠道 | 在背景中自动创建售后或退款 |
| 是否真的结束 | 结果页询问“已解决吗”，失败则给升级路径 | 有解决/未解决/转人工的终态 | 只发送一段答复即计为完成 |

## 2. 可借鉴案例与模式候选

### A. 最高优先级：把动作与规则从生成文本中分离

1. **ABCD（Action-Based Conversations Dataset）**  
   - `事实`：官方仓库提供 MIT 许可的数据与代码；数据集有超过 1 万段真人客服对话、55 个意图，围绕受公司政策约束的多步动作，含 action-state / action-prediction 等任务标签。[项目仓库](https://github.com/asappresearch/abcd)  
   - `可借鉴`：把“用户诉求”和“下一步允许动作”分别建模；对话不是 FAQ 分类，而是受政策约束的状态推进。  
   - `取舍`：领域为电商客服，英文且不等同于设备售后；用于流程、测试灵感，不直接充当产品知识库。

2. **可复现的退款安全边界示例**  
   - `事实`：开源项目 [Customer-Support-Agent](https://github.com/LikhithV02/Customer-Support-Agent) 将 `lookup_customer → get_order → check_refund_eligibility → issue_refund / escalate` 拆成工具；写入动作会独立复跑确定性规则，仓库明确说明模型文本不能绕过该门槛。  
   - `可借鉴`：以“LLM 提议，代码裁决”为原则；用户界面显示工具事件、资格结果、人工升级。  
   - `风险`：是个人开源示例，不是生产系统背书；只复用设计思想和可审查代码片段，先核查依赖与许可证。

3. **DBOS 的可靠退款工作流示例**  
   - `事实`：[官方示例](https://docs.dbos.dev/python/examples/customer-service) 展示订单查询/退款请求；超过金额阈值转人工，并强调审批耗时与进程中断后可恢复的异步工作流。  
   - `可借鉴`：把需要人审的售后申请视为可暂停、可恢复的流程，不阻塞对话。  
   - `取舍`：黑客松 MVP 不引入持久化编排；只在 Demo 中实现“等待确认”的前端状态。若后续接真实流程，再评估 durable workflow。

### B. 信任、控制与可观测性

4. **OpenAI Agents SDK：审批、护栏与追踪**  
   - `事实`：SDK 的 [人机协作指南](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/) 支持暂停等待审批并序列化/恢复运行状态；[工具护栏](https://openai.github.io/openai-agents-js/guides/guardrails/) 可在每个自定义工具调用前后校验；[Tracing](https://openai.github.io/openai-agents-js/guides/tracing/) 默认记录 Agent、模型、工具、护栏和交接的 spans。  
   - `可借鉴`：让“确认”成为工具执行前的真实状态边界，而非仅靠 prompt；为演示留下一条可审计事件流。  
   - `注意`：服务端 tracing 默认开启，可能记录输入/输出；Demo 必须避免真实个人数据，并在上线前审查数据保留与脱敏设置。

5. **LangGraph 的人工审核工具调用模式**  
   - `事实`：[官方指南](https://langchain-ai.github.io/langgraph/how-tos/human_in_the_loop/review-tool-calls/) 用 `interrupt()` 实现批准、修改或以自然语言反馈工具调用。  
   - `可借鉴`：如果已有 Python/LangGraph 基础，适合将“申请售后”节点中断到用户确认。  
   - `取舍`：本项目的共同内核要求单 Agent，不需要多 Agent 图；不要为一个确认节点引入复杂编排。

### C. 可参考的垂直实现（仅作结构/测试借鉴）

- [ecom-support-copilot](https://github.com/LaelaZorana/ecom-support-copilot)：公开仓库将带引用的知识检索、模拟订单 API、确定性退货规则、低置信度/敏感事项人工升级及基于种子工单的回放指标放在一个 Demo 中。适合借鉴“证据 + 规则 + 回放”的演示结构。
- [ecommerce-rag-agent](https://github.com/lingyun1010/ecommerce-rag-agent)：明确区分订单/追踪等实时事实（API）与政策/FAQ（RAG），将激烈退款争议转人工。适合作为本项目数据域分层的佐证；上线前仍须独立审计其许可证、依赖和安全性。

## 3. 适合短期黑客松的技术选型

### 推荐：TypeScript 单体 Web Demo + OpenAI Agents SDK

```text
聊天 Shell
  └─ 单一 Service Agent（状态：澄清 / 诊断 / 计划 / 等确认 / 已解决 / 转人工）
       ├─ search_knowledge（只读：本地 Markdown/JSON，返回引用）
       ├─ lookup_demo_order（只读：固定模拟订单）
       ├─ check_service_eligibility（只读：纯函数规则）
       └─ create_demo_service_case（写入：必须经 UI 确认，写入本地 JSON）
```

| 层 | 建议 | 原因 |
| --- | --- | --- |
| 应用 | Next.js 或 Vite + Express（以团队已有模板为准） | 一个仓库即可交付聊天、工具时间线、确认卡和数据文件；避免微服务 |
| Agent | OpenAI Agents SDK（TS）或直接 Responses API | 有工具 schema、护栏、审批和追踪的一手文档；与单 Agent + 工具目标相称 |
| 知识检索 | 先用 10–20 篇精炼 Markdown + 关键词/小型本地向量检索 | 数据量很小，答案必须带原始段落；不急于引入独立向量数据库 |
| 业务状态 | `demo-orders.json`、`service-policy.ts`、`demo-cases.json` | 使演示可重放、规则可测试，并清楚区分“模拟”与真实系统 |
| 风险控制 | 工具输入 schema、纯函数资格规则、确认 token、事件日志 | 控制边界不依赖模型遵从；便于演示“Ghost 不能越过 Shell 的权限” |
| Evals | 10–15 条固定 JSON 场景，断言工具选择/追问/确认/升级 | 比只看主观演示更能证明闭环 |

`建议`：除非团队已在用 Python/LangGraph，否则不要同时引入 LangGraph、MCP、向量数据库和多 Agent。一个可解释的单 Agent 完成三类工具调用，比“架构大而行为不可信”更匹配当前目标。

## 4. 数据方案：公开数据的正确位置与许可边界

### MVP 数据包（推荐，全部可合成）

| 数据域 | 产物 | 建议内容 | 来源/许可边界 |
| --- | --- | --- | --- |
| 产品知识 | `knowledge/*.md` | 2 个虚构充电/音频产品的规格、指示灯含义、使用限制、FAQ | 自建虚构品牌与型号；不要声称是 Anker 产品资料 |
| 故障诊断 | `diagnostic-flows.json` | 6–8 个症状→关键追问→安全分流→下一步的决策表 | 由团队撰写，附“非真实维修指引、仅 Demo”标记；安全风险直接转人工 |
| 模拟订单 | `demo-orders.json` | 6 个订单覆盖已送达、未送达、过保、重复申请、身份不匹配、金额阈值 | 全部合成姓名、编号、日期和地址；禁止真实个人数据 |
| 服务规则 | `service-policy.ts` | 资格、人工转接条件、必须确认的写入动作 | 以 Demo 假设编写，不暗示为 Anker 售后政策 |
| 对话/评测 | `evals/*.json` | 正常、信息不足、情绪受挫、高风险、安全拒答、未解决升级 | 以 ABCD 的“目标 + 动作 + 约束”思想自行构造；不混入真实聊天记录 |

### 获取与使用检查表

1. 交付包默认只含团队合成数据；公开数据仅用于本地实验时保留原始 LICENSE、来源 URL 和下载日期。
2. 不抓取 Anker 后台、客服记录、订单或未获许可的售后政策；也不把公开网页自动宣称为“官方可训练语料”。
3. 若要改用公开产品手册，逐文件确认版权、再分发和模型使用许可；在 UI 标明来源与版本。
4. 所有演示订单与创建结果显示 `模拟数据 / 不会触发真实售后`；不要使用看似真实的姓名、邮箱、物流单号或地址。

## 5. Demo 场景与验收脚本

### 主故事线：充不进电 + 售后申请

1. 用户：“我的电源产品突然充不进电了，明天要出差，很着急。”
2. Agent 先承接紧急感，提问型号与是否有鼓包/异味/异常发热；解释该信息会决定安全建议和服务路径。
3. 若无安全信号：检索知识条目，给低风险排查步骤及引用；用户表示仍无效。
4. Agent 查询**模拟订单**、运行**模拟资格规则**，展示依据和可选方案。
5. Agent 预览“将创建模拟服务申请”的内容，解释不自动执行，等待确认。
6. 用户确认后才写入模拟案例；给出案例编号和人工支持替代路径，最后询问是否解决。

### 必测反例

| 场景 | 预期行为 |
| --- | --- |
| 鼓包、冒烟、异味、明显过热 | 停止一般排查；给安全提示和人工/紧急渠道；不推荐继续充电或自行拆机 |
| 未给型号但只问一般保养 | 直接给通用低风险建议，不多问 |
| 身份或订单不匹配 | 不透露订单细节；说明所需验证信息或转人工 |
| 不符合模拟资格 | 展示规则原因与替代支持，而非编造批准 |
| 用户拒绝确认 | 不写入；保留继续排查/转人工选项 |
| 用户说“还是没解决” | 明确进入未解决状态并创建/建议人工接管（仍须确认写入） |

## 6. 风险登记与缓解

| 风险 | 后果 | MVP 缓解 |
| --- | --- | --- |
| 模型把猜测说成政策/订单事实 | 误导与失信 | 事实仅来自工具；回答显示引用；无证据即承认未知并转人工 |
| 模型绕过资金/售后边界 | 产生错误承诺或写入 | 写工具内部复跑纯函数规则；UI 确认令牌；未成功工具结果不得显示“已办理” |
| 安全敏感故障给出危险建议 | 人身/财产风险 | 高风险关键词和状态优先拦截；只给停止使用/联系人工的保守建议；不提供拆解或电池维修步骤 |
| 把演示数据误认成真实数据 | 用户误操作或评委质疑 | 每处订单、案例、政策显示“模拟”；README 说明边界 |
| 公开数据许可或用途不兼容 | 无法参赛交付 | 默认合成；引用外部数据时保存许可证并二次核验；iFixit 明确排除 |
| 过度架构导致 Demo 不稳定 | 演示失败 | 单 Agent、本地数据、无真实写操作依赖；每个工具提供可控 fixture |
| 追踪泄漏演示内容 | 隐私风险 | 只用合成数据；开发环境关闭或脱敏 tracing；不把密钥/联系人放进状态 |

## 7. 建议的下一步（按顺序）

1. **锁定主故事线与边界**：采用“充不进电→诊断→模拟售后申请→确认→结果验证”，在需求文档写明不接真实 Anker 系统。
2. **先写 12 条 Eval fixtures**：覆盖第 5 节反例，定义每条允许工具、必要追问、禁止动作与终态；这是实施验收标准。
3. **创建最小数据包**：2 个虚构产品、8 篇 Markdown 知识、6 个模拟订单、1 份规则函数；每个条目均标来源/合成标记。
4. **实现工具边界优先于聊天 UI**：先让资格规则和“未确认不写入”具备单元测试，再接 Agent 与时间线。
5. **演示前做一次人工红队**：输入注入、模糊身份、危险电池症状、拒绝确认、工具失败和“仍未解决”六类必跑。
