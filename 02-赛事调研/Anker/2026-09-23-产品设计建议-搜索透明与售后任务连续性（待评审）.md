# 产品设计建议：搜索透明与售后任务连续性（待评审）

> 状态：用户 Review 草案，尚未转交 Product Agent，也不代表已进入 MVP。  
> 来源：安克品牌与售后横纵分析报告阅读批注；整理日期：2026-09-23。  
> 写作边界：本文件是调研 Agent 汇总的产品设计输入，不是已批准的需求或产品 Spec。

## 1. 背景与目标

阅读调研报告后，用户提出一项明确诉求：**向用户展示 Agent 的搜索过程和检索到的信息，以提高可信度。** 截图中的批注还补充了几个相互关联的设计方向：不同产品类别需要正确路由；售后 Agent 要围绕任务推进，而非只生成答案；建议步骤、用户尝试结果、风险和转人工信息要能连续保留；交给真人时应整理已知信息，并标清尚缺内容；产品设计要把产品知识与服务政策、地区规则区分开。

这些方向共同指向一个产品目标：

> 用户能看见 Agent 根据什么资料采取了什么步骤；Agent 能记住当前售后任务进展，并在自身无法解决时把用户和已有信息顺畅交给下一处理环节。

## 2. 待评审的设计建议

以下各项是**建议 Product Agent 评估的设计输入**，优先级、是否进入当前 MVP 由 Product Agent 决定。

### 建议 A：展示搜索过程与检索结果来源

**用户问题：** Agent 给出故障建议时，用户不容易判断它是否查过正确的型号资料、是否基于可信来源。

**建议体验：** 在答案旁显示“依据与检索”区域，让用户查看：

- Agent 当前识别的产品和问题，例如“eufy Robot Vacuum Omni S1 Pro / T2080；吸力变弱”。
- 本次检索覆盖的主题或资料类别，例如产品支持页、对应故障排查文档、说明书。它不是模型隐含推理的展示。
- 实际检索到并用于回答的资料名称、链接或可打开的来源卡片，以及与当前建议相关的摘录/摘要。
- 哪些资料被采用、哪些没有用于当前建议；如未搜到足够资料，明确说明证据不足，不补造结论。
- 来源适用范围，例如产品型号、地区、页面更新时间（若可获得），避免把一般政策说成特定产品或地区的承诺。

**展示原则：** 展示可核验的检索动作、来源与证据摘要，不承诺展示模型的内部思维链。引用应落到实际支持该建议的资料位置；不同来源冲突时，明确标出冲突并暂停作确定性承诺。

### 建议 B：按产品类别、型号和地区路由知识与流程

**用户问题：** 安克可共享品牌入口，但充电、清洁机器人、音频、储能等产品的知识、风险和售后政策不同；仅凭品牌名不足以选择诊断流程。

**建议体验：** 在给出型号专属步骤或服务政策前，确认产品类别和型号；需要时再确认购买地区/渠道。Agent 应按确认后的产品身份调用对应知识，不把不同品类的诊断知识、风险规则和服务政策混在一起。

**冲突处理：** 如果简称可能指向多款产品、型号或地区信息不足，先澄清再检索/行动；如果来源不适用于当前地区或型号，说明差异，不把其他市场政策直接套用。

### 建议 C：围绕售后任务持续记录状态

**用户问题：** 单轮回答可能无法完成售后问题；若 Agent 不记录步骤和结果，用户或真人接手后会重复沟通。

**建议体验：** 为当前问题维护一份用户可见的任务记录，至少区分：

1. 已确认的产品、型号、问题描述和必要环境信息；
2. Agent 已查阅的资料及其来源；
3. Agent 建议过的排查步骤；
4. 用户明确表示已尝试的步骤及反馈结果；
5. 已识别的风险、未解决项和当前下一步；
6. 当前状态，例如“排查中”“等待用户反馈”“建议转人工”“交接待确认”。

**记录规则：** “Agent 建议过”不等于“用户已完成”；用户未确认的结果应标作未知，不自动补齐。跨轮次继续时，先简短回顾当前状态，让用户可以纠正。

### 建议 D：将人工接管设计成正常流程，并整理交接数据

**用户问题：** 排查无法解决时，如果 Agent 只显示“联系支持”，用户仍要从头描述；如果把不准确的承诺带入售后，反而会增加误解。

**建议体验：** 当证据不足、排查已完成仍未解决、涉及安全/保修判断，或用户主动要求人工时，Agent 应说明转交原因，并生成一份可预览、可修正的交接摘要：

- 用户确认过的产品身份与问题；
- 已查阅的来源；
- 已建议步骤、用户实际执行步骤及各自结果；
- 仍未解决的现象；
- 已具备和仍缺少的材料；
- 当前已知的风险与下一步建议。

只有在用户确认后，才执行产品实际支持的交接或建单动作。若 Demo 仅在本地生成记录，应明确显示“本地记录，未提交给安克客服”；若没有真实人工入口或状态接口，不显示“已转接/已建单/处理中”等会造成误解的状态。

### 建议 E：区分产品知识、服务政策与系统能力

**用户问题：** 用户容易把“Agent 给了排障建议”误解成“它查过订单/保修并可替我申请维修”。

**建议体验：** 对回答和操作分别标明能力边界：

- 产品知识回答：注明适用型号与来源；
- 服务政策说明：注明适用地区/渠道和来源；
- 真实系统操作：显示实际执行结果及可追踪编号（仅在系统确实支持时）；
- Demo 模拟能力：标注为模拟或本地演示。

Agent 不应仅凭公开故障文章判定保修资格、库存、换新/退款结果或维修时限。

## 3. 建议的端到端体验草图

```text
用户描述问题
    ↓
确认产品类别 / 型号 / 必要的地区信息
    ↓
展示检索状态与命中的资料来源
    ↓
基于对应资料给出一个可执行步骤
    ↓
用户反馈结果 → 更新“已尝试 / 结果 / 未解决项”
    ├─ 已解决 → 展示依据并确认结果
    └─ 未解决 / 需要人工
         ↓
       说明原因，整理资料与缺口
         ↓
       用户预览、修改并确认
         ↓
       执行真实可用的转接/建单；否则注明仅生成本地记录
```

这张流程图是待讨论的产品体验方向，并不代表当前产品已经具备上述集成。

## 4. 可用于评审的验收问题

Product Agent 可评估是否将以下问题写入 Spec：

- 用户能否辨认 Agent 当前处理的产品类别和准确型号？
- 用户能否打开或核对本次回答所依据的来源？来源是否支持眼前这条建议？
- 检索结果不足、型号不匹配或地区不适用时，Agent 是否会先澄清或说明限制，而非给出确定结论？
- 用户能否区分“Agent 建议过”与“我已经做过”？Agent 是否记录反馈和当前进度？
- 未解决时，交接摘要是否能准确呈现已知事实、已尝试步骤、结果、来源和缺口？
- 本地 Demo 是否明确区分本地记录和真实服务申请？系统未返回成功时是否不会显示“已提交”？
- 用户是否可以查看、修正并确认交接内容？

这些是供 Product Agent 取舍的验收问题，不是已承诺的开发清单。

## 5. 当前 T2080 示例的适用边界

已有调研确认 eufy Robot Vacuum Omni S1 Pro 的机器人型号为 T2080，官方支持资料包含吸力变弱排查文章。可用该案例展示：先确认机器人型号；展示对应官方资料；按资料分步建议；记录用户是否实际尝试以及结果；必要时生成带来源和未解决项的交接摘要。

当前公开证据**不能**证明 Demo 可访问安克账号、订单、设备遥测、真实 CRM 工单、保修审核、备件库存或真人客服转接接口。上述能力如未取得真实接口和授权，应明确保持为未接入，不在交互上冒充真实服务状态。

## 6. 需要 Product Agent 决定的问题

1. “展示搜索过程”希望覆盖到什么颗粒度：只展示命中资料与引用，还是也展示检索主题/关键词、筛选结果和未命中状态？建议先以“可核验检索状态 + 实际采用的来源卡片 + 证据不足提示”为最低候选。
2. 当前 T2080 Demo 是否把任务状态记录、用户反馈和交接摘要作为核心闭环的一部分？
3. 首次 MVP 的人工接管是仅输出本地交接记录，还是有已授权且真实可用的外部服务入口？
4. 用户可见来源是否需要提供原文链接、文档段落定位、检索时间和地区/版本信息？哪些信息在当前知识数据中实际可得？
5. 对型号与地区澄清，哪些字段属于开始排障的必要条件，哪些只在用户选择转人工时再收集？
