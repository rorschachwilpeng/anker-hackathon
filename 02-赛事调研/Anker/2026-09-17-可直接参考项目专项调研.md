# Anker 智能服务：可直接参考项目专项调研

> 调研日期：2026-09-17（Asia/Shanghai）。范围是可运行、可 fork 或可低成本改造的公开项目与数据；不假设 Anker 内部数据或真实服务权限。  
> 核验口径：仓库/官方文档能提供启动、Docker 或测试命令，记为“文档可运行”；**本轮未在本机部署第三方项目**。许可证和维护状态均为访问日快照，复制代码或纳入交付前仍须锁定 commit/tag 并复查 LICENSE。

## 1. 结论

**最短可复用路径不是把客服平台、低代码平台和 RAG 系统拼在一起，而是 fork 一个已带“工具状态可视化”的聊天样例，补入本地知识/订单 fixture 与确定性确认门。**

建议实际复用组合：

1. 以 [OpenAI ChatKit Customer Support sample](https://github.com/openai/openai-chatkit-advanced-samples/tree/main/examples/customer-support) 的 FastAPI + React 对话与右侧状态面板为壳；
2. 以 [support-agent-hitl](https://github.com/gaurav-oberoi/support-agent-hitl) 的 `approve / deny → 状态是否写入` 测试语义为售后申请确认门；
3. 以 [provenance-energy-rag-chatbot](https://github.com/s26-redi-ml-ai/provenance-energy-rag-chatbot) 的“来源卡、无依据拒答、故障码精确查询”作为知识诊断的交互基线；
4. 数据完全采用自建虚构产品、故障流、订单与规则。ABCD/ESCI/Faker 仅用于测试设计或生成无真实身份的 fixture。

`建议`：这不是把三个仓库直接合并，而是仅迁移最小的交互/测试机制。Chatwoot 和 Dify 留作“人工工作台/低代码替代路径”参考，不纳入 48 小时主实现。

## 3. 关键项目核验笔记

### 3.1 ChatKit Customer Support：最适合作 48 小时 UI 起点

- `事实`：官方样例将 FastAPI 后端与 React 前端配对；客服案例使用每线程 `AirlineStateManager`，把客户画像、行程、近期动作注入上下文，并为改座、取消、餐食等行为提供工具和界面同步。[官方仓库 README](https://github.com/openai/openai-chatkit-advanced-samples)  
- `事实`：客服子项目给出后端 `uv sync && uv run uvicorn`、前端 `npm install && npm run dev` 的启动步骤；需要 `OPENAI_API_KEY` 和开发/生产不同要求的 ChatKit domain key。[子项目 README](https://github.com/openai/openai-chatkit-advanced-samples/blob/main/examples/customer-support/README.md)  
- `推断`：将“航班/座位”替换为“产品/诊断步骤/模拟订单/服务申请”是表层适配；保留工具输出可见化更能服务共同内核。  
- `风险`：API 与域名 key 是运行前置；没有看到抓取页明确许可证标识前，不应复制源码。

### 3.2 support-agent-hitl：确认门的最小参考

- `事实`：退款会先暂停并保存状态，只有对同一线程 resume 为批准时才执行；7 个 fake-model 测试检查批准、拒绝、状态查询和未知订单路径，且这些测试不需 Ollama 或网络。[仓库](https://github.com/gaurav-oberoi/support-agent-hitl)  
- `推断`：对 Anker Demo，可将“退款”改为“创建模拟售后申请”；不必引入多 Agent 或真实金钱动作。  
- `风险`：低关注度个人仓库不等于低质量，但必须把安全保证写成自己的测试，而非转述 README。

### 3.3 provenance-energy-rag-chatbot：把“可解释诊断”收敛到可测试行为

- `事实`：项目的 MVP 要求答案显示文件、页码（可用时）、chunk、相关分和证据片段；没有足够文档证据即拒答。另有不调用 LLM 的精确故障码查询、citation validation、mock 模型/嵌入、pytest、Docker 说明。[仓库](https://github.com/s26-redi-ml-ai/provenance-energy-rag-chatbot)  
- `推断`：这些模块比“换一个向量库”更值得复用：用户可以看到诊断依据，也能区分“我不知道”和“我猜测”。  
- `风险`：默认允许 general knowledge 的模式不宜用于有安全含义的设备建议；Demo 应默认来源不足即升级/拒答。

### 3.4 Chatwoot：人工接管应是会话状态，不是结束语

- `事实`：官方 AgentBot 文档定义了 webhook 接收事件、调用外部 API、回写消息，并允许将会话状态改为 `open` 交给人工；人工还可将其改回 `pending` 让 bot 再处理。文档最后更新于 2026-05-19。[官方文档](https://www.chatwoot.com/hc/user-guide/articles/1677497472-how-to-use-agent-bots)  
- `事实`：官方仓库说明其为自托管客服平台，含多渠道 inbox、联系上下文、Help Center 和协作能力；组织页快照标注主仓库 MIT、2026-05-27 更新。[仓库](https://github.com/chatwoot/chatwoot)  
- `建议`：只借鉴 `pending/open` 的职责边界与交接数据包；不在 Demo 中部署完整客服平台。

### 3.5 Dify：成熟，但不是当前最低成本路径

- `事实`：Dify 提供 workflow、RAG、工具、可观测性；版本页显示 2026-09 的 v1.17.1 release。其 `ask_human` 层会把 deferred call 交给客户端收集结果后以 `deferred_tool_results` 启动后续运行。[仓库](https://github.com/langgenius/dify)、[ask-human 文档](https://github.com/langgenius/dify/blob/main/dify-agent/docs/dify-agent/user-manual/ask-human-layer/index.md)  
- `事实`：其许可证是带额外条件的 Dify Open Source License，不是无条件 Apache-2.0；包含多租户和前端标识相关条件。[LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)  
- `建议`：若团队已熟悉 Dify，可以单独用它快速演示检索/流程；否则不把完整实例接入主 Demo。

## 5. 48 小时最短复用组合

### 组合与范围

```text
ChatKit support UI（fork，替换航空数据）
  └─ 单一 Service Agent
       ├─ search_demo_knowledge → 本地 Markdown/JSON + 来源卡
       ├─ lookup_demo_order → 合成订单 JSON
       ├─ check_demo_eligibility → 纯函数，不写入
       └─ create_demo_service_case → UI 确认后才写 demo JSON
```

| 时间 | 只做这些 | 可验证结果 |
| --- | --- | --- |
| 0–8 小时 | 起 ChatKit sample；删除航空专属字段；放入 2 个虚构产品与 6 个模拟订单 | 页面可启动，明确显示所有数据均为模拟 |
| 8–20 小时 | 接 3 个只读工具；移植来源卡/故障码精确命中思想 | 一条“无法充电”对话能给来源或明确无依据 |
| 20–30 小时 | 加资格纯函数和确认卡；按 support-agent-hitl 写批准/拒绝测试 | 未确认不写入、拒绝不写入、批准生成模拟案例 |
| 30–40 小时 | 加高风险安全分流、工具失败、未解决升级状态 | 高风险不继续排障；失败可说明并改走人工路径 |
| 40–48 小时 | 固定 10–12 条 eval fixtures、录制演示、断言工具/终态 | 能重跑并验证：少问、依据、确认、完成/未解决 |

### 明确排除

- 不接真实订单、退款、物流、CRM、支付、邮件、聊天渠道或 Anker 内部系统。
- 不部署 Chatwoot、Dify、Celery/Redis/Qdrant 的整套系统；本地 Markdown/JSON 足够验证闭环。
- 不将公开手册/维修指南自动抓取后当作可用知识库；每份外部内容先确认许可和安全边界。

## 7. 风险与复用前检查

1. **许可证先于复制。** ChatKit sample、`appliance-ai-assistant`、`Ecommerce RAG Agent` 的本轮页面抓取未展示清晰许可时，不复制实现；Dify 明确有额外条件。
2. **运行前固定版本。** fork 后锁定 tag/commit、Python/Node 版本与依赖锁文件；不要在演示当天追最新 main。
3. **真实写入不可模拟成真实。** 所有订单、资格、案例编号和完成状态均要带 `demo` 标识，界面中不能说“已为您提交真实售后”。
4. **手册与安全内容需单独核验。** 来源卡只能证明“引用了某段文本”，不能证明该文本对设备安全可执行；高风险电池/发热/鼓包等场景应停止排障并走人工安全分流。
5. **不展示隐藏推理。** 可见的是工具、依据、规则结论和用户确认，不展示 chain-of-thought 或无关内部信息。
