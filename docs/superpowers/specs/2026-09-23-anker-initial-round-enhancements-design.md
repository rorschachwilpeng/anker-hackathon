# Anker 智能客服初赛增强设计

状态：待 Product Lead 审阅；本文件定义下一阶段目标与验收，不是实施步骤。日期：2026-09-23。

## 1. 结论与基线

本轮不重做客服底座。先把已验收的文字售后切片接入正式开发线，再沿同一条服务链路补充图片线索、情绪与紧迫性回应、结构化工单交接和少量有来源的知识。界面只做支持这条链路的必要改动。初赛材料应区分已验证能力、计划实现能力和后续设想，不用功能数量代替可信度。

当前已验证版本位于 `codex/anker-s1pro-implementation`，提交 `8df71a2`；它覆盖 T2080 吸力变弱的文字追问、官方知识检索、逐步反馈、用户确认后建单及本地只读工单查看。验收记录见 `06-评估验证/2026-09-23-S1-Pro-垂直切片验收.md`。这不等于图片、情绪或多产品服务已经实现。

目标读者是 Product Lead 与唯一 Technical Builder。本 spec 获批后，另写实施 plan，再按正式交接规则派给 Builder；不在本文件中授权直接改代码。

## 2. 用户结果与范围

初赛演示应让用户在一个售后会话中描述问题，必要时补一张图；系统只把图片和文字当作线索，先确认关键歧义，再给出适用型号、有来源的一步建议。用户反馈无效或没有可靠依据时，经明确同意建立工单，人工能看到已确认事实和未解决事项。用户应看得出系统正在澄清、查资料还是提交工单，且不会把“提交成功”误认为“人工已经处理”。

本轮以已验证的 T2080 案例为主线；知识可以增补少量同型号的官方问题或一个额外产品的资料，但额外产品不得成为主链路验收的前置条件。图片理解是图文线索提取，不是图像向量检索或自动故障诊断。订单、保修资格、真实账号绑定、自动派单、SLA、多 Agent 与公网部署均不在本轮范围内。

| 优先级 | 本轮交付 | 可削减边界 |
| --- | --- | --- |
| P0：不得退化 | 把已验收切片安全接入 `codex/product-agent-development`；保留原文字主链路、来源、确认门禁和建单幂等 | 若增强功能不稳定，回退到这条可演示链路 |
| P1：核心增强 | 单张图片的可见线索提取与确认；明确情绪/紧迫性的回应；结构化交接数据；对应测试证据 | 图片理解失败不得阻断纯文字咨询；不扩大到图片检索 |
| P2：演示体验与内容 | 统一会话中的处理状态提示、少量来源明确的知识和图文样例 | 以主链路稳定为先；不做完整客服工作台或大规模产品覆盖 |

## 3. 系统协作

```text
用户文字 + 可选单张图片
  → 输入校验与图像可见线索提取
  → 本轮理解：产品候选、症状、已表达的情绪/紧迫性、反馈
  → 会话任务状态：已确认与待确认的事实、已试步骤、工单状态
  → 条件流程：追问 / 查对应型号知识 / 给一步建议 / 提议人工
  → 用户明确同意后创建工单
  → 同一会话展示结果、来源和真实处理状态
```

模型负责提取线索、形成候选理解和组织自然语言；程序负责图片输入边界、产品确认、知识型号过滤、工单确认与去重、失败状态和持久化。图片或模型输出不能绕过现有硬约束。现有检索和工单能力是被调用的业务能力，不因为加入多模态而重写。

### 3.1 图片入口与多模态理解

- 用户每轮最多补充一张 JPEG/PNG 图片；页面应允许纯文字提交。图片大小上限设为 5 MB，超限或格式不支持时明确提示，不发送给视觉模型。
- 视觉理解只输出可见事实或候选：可读的标签/型号文字、可见报错、产品外观线索、看不清或相互矛盾之处。输出需区分“图片直接可见”“模型推测”“用户文字陈述”，不得把推测写成已确认事实。
- 图文一致且仍有关键歧义时继续追问；图文冲突、型号看不清或无法确认时，只向用户核实一个影响后续路径的问题。未确认型号不进入专属排障。视觉模型不得根据外观断言内部故障。
- 图片处理失败时保留用户文字和已有任务状态，提示可重试或用文字补充；不得伪称已经看懂图片。初赛本地演示的图片引用只存于受控本地存储，数据库保存引用和提取出的线索，不把图片二进制或演示用户图片提交到 Git。若无法安全保存原图，工单应明确标记“图片未留存”，不伪造人工可查看的附件。

### 3.2 情绪与紧迫性

- 只根据用户本轮明确表达的抱怨、焦虑、使用期限或影响提取服务线索；保存具体依据（例如“明天要使用”），不保存“愤怒用户”等长期标签。
- 回复先承认具体处境，再给出当前能做的一步。紧迫性影响回复顺序与是否尽快提出人工接续，不意味着承诺加急、优先派单或服务时效。
- 不应让情绪判断覆盖事实门禁：着急也不能跳过型号确认、虚构知识或未经同意建单。情绪判断失败时仍走正常售后流程。

### 3.3 工单交接数据

工单仍表示一次需要后续处理的服务诉求，不等于购买订单。现有 `tickets` 表主要以一段描述承载摘要；本轮在不破坏旧工单和原客服回归的前提下，为售后交接保存可查询的结构化字段或独立关联记录，具体数据库迁移方式留给实施 plan。

| 字段组 | 最少内容 | 数据边界 |
| --- | --- | --- |
| 关联与状态 | 工单号、会话 ID、创建时间、真实创建状态 | “待确认”“创建失败”不是“已创建”；重复确认只对应一张工单 |
| 产品与诉求 | 用户原话、已确认产品型号、症状、待核实问题 | 候选型号不得写成已确认型号 |
| 排障过程 | 建议过的步骤、用户明确反馈、未解决事项、知识来源 | 建议过不等于用户已尝试；未反馈保持未知 |
| 图文证据 | 图片引用及可见线索、用户明确表达的时间约束 | 无图片或未留存原图时如实为空；不记录未经核实的视觉推断为事实 |
| 操作证据 | 用户建单确认、创建结果 | 便于核对授权与失败，不自动生成真实订单或保修结论 |

客服侧本轮仅需能查看交接信息，不新增分派、状态管理、人工实时接管或权限系统。现有本地无鉴权查看页只能用于受控演示，不得作为公开部署入口。

### 3.4 知识与会话界面

新增知识必须有可访问的来源、产品型号和采集日期；原始资料、文字知识片段及测试图片分别记录来源。图片用于验证识别与消歧，不因有一张产品图就宣称支持该产品的完整排障。已有官方知识的型号过滤与来源展示保持不变。关键词检索、重排序和跨产品扩库先通过测试确认缺口，再决定是否实施。

面向消费者保留一个连续的售后会话：显示“正在识别图片/等待产品确认/正在查资料/等待排障反馈/等待建单确认/工单已创建或失败”等可理解的状态。状态文案来自实际流程结果，不用纯动画假装工具已经成功。可以保留旧电商演示入口作回归，但 Anker 主案例不应要求用户手工切换到另一个对话框。

## 4. 错误与降级

| 情况 | 期望行为 |
| --- | --- |
| 图片不可读或模型失败 | 保留文字和已确认状态，说明图片无法可靠识别，向用户要文字或更清晰图片 |
| 图文冲突或相似型号 | 暂停型号专属建议，追问确认；不能按模型置信措辞直接放行 |
| 检索为空、来源缺失或型号不匹配 | 不给具体排障步骤，说明缺少可靠依据，提供人工接续路径 |
| 模型/工具调用异常 | 返回可理解的失败状态，允许有界重试；不丢失已试步骤和反馈 |
| 用户未确认建单或建单失败 | 不创建或不宣称成功；失败后保留交接摘要，重试不得重复建单 |

## 5. 验收与实现顺序

先验收已跑通切片在正式开发线上的运行与回归；再做图片线索和情绪回应；接着补工单结构化交接及会话状态展示；最后加入少量官方案例、图文测试与演示材料。各项实现可以并行准备资料，但任何增强不得损坏 P0 链路。技术方案、接口、迁移脚本及任务拆分在下一份实施 plan 中确定。

验收以可复现行为为准：

1. 旧文字十类样例和主链路继续通过；原电商底座回归无新增失败。
2. 至少覆盖清晰型号图、模糊图、相似产品图、可见报错图、图文冲突和无图片输入；逐例记录预期追问/检索/降级动作及实际结果。测试图像须有使用权或明确来源。
3. 至少覆盖明确抱怨、明确使用期限和中性咨询；核对回应是否贴合已表达事实，且不承诺未提供的时效。
4. 从一条真实演示会话创建工单后，客服侧能分辨已确认/待核实信息、建议/已尝试步骤、图片是否留存及实际创建状态；未经确认和重复确认仍满足原门禁。
5. 演示中可见状态、知识来源和失败提示与后台真实结果一致；图片、模型或检索失败时，纯文字主链路仍可继续。

9 月 26 日前冻结可演示版本、完成回归、录屏与方案材料；9 月 27 日不安排依赖当天完成的新开发。若进度不足，依次削减额外产品、界面润色、情绪细化；保留已验证文字链路、可信来源、确认门禁和真实建单状态。
