# ch03 知识库与 dense 语义检索设计

状态：已按最新需求整理并自审，待用户审阅；尚未进入实施计划与产品实现。

## 已确认的需求

给现有客服聊天增加语义知识检索，query_faq 的参数和返回字段不变。用户指定 FastAPI、SQLAlchemy、MySQL、Milvus、LangChain 与 BGE-M3；只做 dense 在线检索，不做关键词召回、混合检索、重排或 Agent 循环。

BGE-M3 使用硅基流动云端，地址 https://api.siliconflow.cn/v1/embeddings，模型 BAAI/bge-m3。独立 EMBEDDING_* 配置保存在 ecommerce-support/.env，原 OPENAI_* 继续供客服回复和离线抽取使用。本机不下载模型或安装推理依赖。已实测 HTTP 200、1024 维有限数值向量，测试消耗 8 tokens；这不代表知识检索验收已通过。

客服、MySQL、Milvus 和离线 worker 在本地；Milvus 通过 Docker 启动。保留 ch02 四张表及数据。新建 knowledge_chunks 和 qa_extraction_staging，严格采用用户提供的字段、类型、默认值、索引、自引用外键和 utf8mb4。初始化包含 SET NAMES utf8mb4，不重建已有表。

## 方案选择与待批准事项

推荐独立建库 CLI + 单个定时 worker。与 FastAPI 内定时器相比，应用重启和多进程不会重复启动任务；与新增消息队列相比，部署更简单。定时 worker 默认 Asia/Shanghai 每天 02:00 执行一次，也提供手动命令和显式关闭配置。

建议新增一张辅助表 knowledge_ingestion_state，业务两表保持原样。字段为 state_key VARCHAR(191) 主键、payload JSON NOT NULL、created_at、updated_at；采用 InnoDB/utf8mb4。它存批次扫描上界、抽取检查点、来源到 chunk 的映射、内容指纹、暂存行归并结果和失败摘要。一个来源或任务一条状态记录，不把全库塞进一个 JSON。具体 SQL 在计划中列明。

这是本设计唯一需要扩展用户 DDL 的事项：如果仅用本地文件保存这些状态，文件和 MySQL 无法同事务提交，恢复逻辑更复杂；仅凭 pending/done 也无法识别重复导入来源。因此推荐持久化辅助表，而非修改两张业务表或依赖内存状态。

## 文档处理

按 Markdown 标题树解析；围栏代码中的 # 不作为标题。政策和手册的 questions 保存本节标题，category 保存上级标题路径；根章节无父标题时使用文档标题。FAQ 的 questions 保存真实问法，多个问法换行分隔，数据库类型为 TEXT，不使用 JSON。

先按章节，再按段落、完整句子递归切分。初始软目标为 1200 UTF-8 字节，句界重叠目标 200 字节；重叠取完整句子后缀，必要时缩短至零以保证前进，不截取半句。英文及中文句末符均识别。表格按完整行切分，每块复制表头和分隔行，表格块不套句子重叠。相邻块指针只连接同一来源下的顺序块。

云端 BGE-M3 每条文本上限为 8192 tokens。本章不在本机安装模型 tokenizer，采用保守 UTF-8 字节上限 6000（包含分类、问法和模板）限制请求，并处理上游明确的超限响应；不把字节数称为精确 token 数。单句、单行或代码块无法在硬限制内完整容纳时，报出来源并停止该来源导入，不静默截断或漏掉条款。

is_key_clause 由显式文档标记指定；不使用 LLM 改写政策原文。只将 category、questions、answer 按固定标签和顺序拼接做嵌入。section_path、content_type、is_key_clause、前后指针及运行状态只保存为元数据。

使用已有演示 FAQ 扩展生成明确标注为演示资料的 Markdown，包含运费、退货、商品 FAQ、售后手册、长表；后续可从指定目录导入用户真实资料。

## 历史对话抽取与去重

只处理已结束会话的完整轮次，读取消息时必须保留 assistant 工具申请和对应 tool 结果。首次运行固定扫描上界，以会话 id 分页，每批默认 20 个会话；按模型输入预算再拆小批，避免串味。worker 定期扫描，可发现后来结束的旧会话，通过来源状态避免重复抽取。

LLM 结构化抽取真实 question、证据支持的 answer、category 和证据消息 id。question/answer/batch_no/source_ref 写入 qa_extraction_staging；分类和证据映射放辅助状态表，source_ref 使用短来源标识而非塞入整段 JSON。暂存行插入、分类映射和批次检查点在同一 MySQL 事务内提交；LLM 请求在事务外执行。断点前未提交的批次可重新请求，已提交批次不重复插入。

排除 mock 订单、商品、物流事实，失败或未完成回复，含个人信息的内容以及缺乏证据的店铺承诺。来源矛盾或无法归类的记录保留 extracted 并在任务报告中标记待核，不进入知识库。

本次抽取全部批次结束后，针对所有 extracted 暂存记录及既有知识整体去重。先规范化文本处理完全重复；对剩余记录使用离线 dense 候选加 LLM 判断同一事实，合并真实问法。冲突不覆盖权威政策；离线去重不改变在线 dense 单路范围。

新知识写入、暂存 kept/discarded 标记及暂存到知识映射同事务提交。合并问法会将目标知识置 pending，重新向量化。先完成本次归并与向量化再标记任务完成，默认保留暂存审计数据，不自动清空。

## MySQL 与 Milvus 双写

Milvus knowledge 使用显式 INT64 主键 id、1024 维 FLOAT_VECTOR、content_hash 字符串，auto_id=False，COSINE 相似度。MySQL BIGINT UNSIGNED 的值在写 Milvus 前检查不超过有符号 INT64 上限。vector_id 回填主键的十进制字符串。

导入按来源身份和块序号映射复用 chunk id；来源指纹、块映射、嵌入配置指纹保存在辅助状态表。所有导入和抽取归并命令使用同一 MySQL 会话级互斥锁，持有独立连接，连接失效就停止任务；不让多个 writer 同时变更源。在线读无需锁。

顺序：MySQL 提交 pending 原文和状态 → 云端编码 → Milvus upsert 同一 id → 核对返回 id → MySQL 条件核对原文快照后回填 vector_id、done。外部请求不放入长 MySQL 事务。Milvus 已写成功但 MySQL 未回填时，重跑相同 id，仍只保留一条向量。

content_hash 对固定嵌入文本计算；查询回 MySQL 后重新计算并对照 Milvus 的 hash，且要求 done。模型配置改变时，显式将相关知识置 pending 并重建；托管服务不承诺不可变模型版本，验收记录返回模型名和配置指纹，不虚构固定模型修订号。

内容变化先提交 pending，再更新向量；删掉的来源块先删除 MySQL 原文，外键按用户 DDL SET NULL，再删除 Milvus 向量，状态表保留待清理 id 直到成功。这样残留向量不会成为可返回的过期原文。重建邻块链接在同一事务内完成。

## 在线聊天接入

现有 app/tools/business.py 的 query_faq(keyword: str) 保留参数名、1–64 字符约束及返回结构：keyword、found、items；每项仍为 id、question、answer、category。更新“只支持字面匹配”描述，让模型保留用户原始主题或短问题，不人为将邮费改成运费。

工具通过知识检索服务执行：云端嵌入 → Milvus Top-K（初始 5）→ MySQL 按相似度顺序回查 → done/hash 校验 → 阈值过滤 → 旧输出格式。阈值由正负标注集校准后写配置，另用留出样例验收。无有效命中 found=false；云端或 Milvus 故障返回现有工具错误，不回退 SQL LIKE。

当前工具结果预算为 2048 字节，适配层按序装入完整短块；一个块装不下时不截取关键条款，也不截断 JSON，而是跳过该块并记录预算诊断。通过切分评估确认运费/退货关键块可完整进入回答。若关键正例因预算无法回答，必须在验收前调整块大小或提出有依据的预算调整。

SSE 工具状态、工具徽章、单轮工具执行和最终逐 token 回复复用 ch02。嵌入超时与工具总超时统一配置，重试必须在总截止时间内，避免请求结束后遗留调用。

## 组件边界与实施顺序

1. 数据层：用户两表、辅助状态表、初始化校验、来源和任务事务。
2. 文档层：Markdown 解析、句界和表格切分、三字段拼接、演示资料与标注集。
3. 索引层：云端嵌入客户端、Milvus 适配器、可恢复建库 CLI。
4. 抽取层：有证据的结构化抽取、全局归并、定时 worker。
5. 在线层：知识检索服务注入 query_faq，更新工具说明与上下文预算处理。
6. 验收：真实建库检索、两处中断恢复、聊天端到端演示与评审。

这只是设计中的任务分解；详细实施计划待本设计审阅后编写。涉及库或 API 的实现前先查询 Context7，版本不兼容时报告，不换选型。
