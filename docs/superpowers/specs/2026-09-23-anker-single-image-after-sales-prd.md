# Anker 售后单张图片辅助咨询 PRD

> 状态：待审阅｜2026-09-23
> 类型：多模态第一阶段的产品需求与交付计划；不是逐文件编码清单。
> 对应设计：[初赛增强设计](2026-09-23-anker-initial-round-enhancements-design.md)

## 1. 一句话说明

让用户在现有售后对话中补充一张产品或故障照片。系统先提取**图片里看得见的线索**，结合用户文字追问关键歧义；确认产品后，仍用现有的**文字知识库**给出有来源的排障建议。本轮不做图片向量、图片相似检索，也不顺带开发情绪与紧迫性识别。

## 2. 背景与要解决的问题

当前已验收的垂直切片只能处理文字：用户说“S1 Pro 不吸了”，系统确认产品、查询 T2080 官方文字资料、逐步排障，在用户同意后建工单。实际售后求助中，用户可能更容易拍下型号标签、报错界面或设备外观，却说不清标签文字或故障现象。没有图片入口，系统只能反复要求文字描述；若看到了图片却把不清楚的线索当成事实，又会把用户带向错误型号的资料。

本 PRD 要解决的是“图片帮助澄清本次求助”，不是“建立多模态知识库”。现有 MySQL 知识元数据、Milvus 文字向量和按型号过滤的检索链路继续使用。初赛主案例仍是 eufy Robot Vacuum Omni S1 Pro（T2080）的吸力变弱；它是验证用案例，不代表产品只服务这一款设备。

开发依赖：已验收切片目前在 `codex/anker-s1pro-implementation`（`8df71a2`），尚需安全接入正式开发线 `codex/product-agent-development` 并重跑文字回归。不得在未确认集成基线的情况下，用多模态改造覆盖已验证链路。

## 3. 目标、指标与非目标

| 目标 | 验收口径 |
| --- | --- |
| 用户能补充图片 | S1 Pro 售后演示入口支持单张图片与可选文字；能预览、移除，发送后看到自己提交的图片提示 |
| 图片确实参与理解 | 服务端返回或记录本轮可见线索与不确定项；清晰的标签/报错用于形成候选，模糊图明确表示无法判断 |
| 不因图片误用知识 | 产品尚未由用户确认、图文冲突或型号不清时，不能输出 T2080 专属排障步骤 |
| 保住已有闭环 | 文字原链路和工单确认门禁不退化；图片失败时仍能继续文字咨询 |

首批验收集至少包含 8 类输入：清晰型号标签、同名但不同品类产品、模糊标签、可见报错、图文冲突、只有图片、只有文字、视觉服务失败。逐例记录预期动作、实际动作和来源；**8 类均须通过“未确认不提供专属步骤、失败不伪称识别成功”的安全判断**。清晰图能否正确提取文字另单独统计，不用“模型感觉识别得不错”代替结果。原文字十类样例与三轮主链路继续作为回归基线。

本轮不做：图片入知识库、图向量或图搜图；批量图片/视频；自动识别内部故障；由图片直接判定保修资格；真实订单或账号绑定；情绪和紧迫性识别；统一全部客服入口的重设计；完整客服工作台。

## 4. 用户与使用场景

目标用户是正在咨询产品使用或故障的消费者，尤其是不知道怎样描述型号、报错或外观异常的人。用户的任务不是“完成图片上传”，而是让客服更快确认**到底是哪款产品、出现了什么可见现象、下一步该检查什么**。

主路径：用户说“我的 S1 Pro 不吸了”并上传标签或设备照片 → 系统提取可见线索 → 询问是否为 eufy 扫拖机器人 S1 Pro → 用户确认 → 调用原有 T2080 文字知识检索 → 给出一步排障建议与来源 → 继续收集反馈。若图片其实指向另一类同名产品，系统应指出需要重新确认对象，不得套用 T2080 的资料。

## 5. 需求与交互

| 优先级 | 需求 | 验收标准 |
| --- | --- | --- |
| P0 | 在现有 S1 Pro 对话输入区加入“添加图片”控件 | 仅接受一张 JPEG/PNG，最大 5 MB；选中后显示预览和移除入口；可发送“文字＋图片”或仅图片 |
| P0 | 提交时展示真实处理状态 | 选中、上传/分析中、等待确认、分析失败和回复完成有对应提示；没有拿到服务端结果前不显示“识别完成” |
| P0 | 从图片提取可见线索 | 输出可读的标签/型号文字、报错文字或外观线索及看不清之处；字段为空代表未知，不以推测补值 |
| P0 | 图文联合消歧 | 图片线索与用户文字一致时形成产品候选；冲突、模糊或同名产品时提出一个关键追问；只有图片且症状未知时先问用户遇到了什么问题 |
| P0 | 接入原售后流程 | 用户确认产品后，继续走现有按型号检索、单步排障、反馈和确认后建单；不新增图像检索链路 |
| P0 | 错误恢复 | 格式/大小错误在发送前提示；视觉调用失败或超时时保留文字与会话状态，明确告知无法可靠读取图片，允许改用文字继续 |
| P1 | 交接保留图片线索 | 本次会话和已有工单摘要可区分“用户原话”“图片可见线索”“用户确认事实”；不把未确认视觉候选写成确定结论 |

上传控件只加在当前 S1 Pro 售后演示入口；原电商聊天与售后提取入口保持原样。用户撤销所选图片后，该轮恢复纯文字发送。发送中的重复点击不得产生两次上传或两条用户消息。界面显示图片缩略图只用于本次页面会话；若刷新后原图不可恢复，须如实处理，不假装图片仍在服务端。

### 服务过程中的文案原则

- 图片清晰但身份未确认：“照片上看到了……，请确认这是您要咨询的产品吗？”
- 图片看不清：“这张照片里的型号/报错我无法看清。可以补一张更清晰的照片，或直接告诉我标签上的文字吗？”
- 图文冲突：“您文字中提到……，照片看起来可能是……。为避免给错步骤，先确认您要咨询哪款产品。”
- 图片处理失败：“图片暂时没能读出来。文字描述我已保留，我们可以先根据您提供的信息继续。”

具体回复可自然变化，但不能宣称图片证明了不可见的内部故障，也不能把模型的候选判断说成用户已经确认的事实。

## 6. 方案与数据边界

```text
前端选图、预览并提交
  → 服务端校验格式和大小
  → 视觉模型提取“可见线索＋未知项”
  → 与用户文字合并为本轮候选理解
  → 现有任务状态判断是否追问
  → 用户确认产品后，调用现有文字知识检索
  → 原排障／反馈／确认建单流程
```

这是一条 Agent 输入能力的增量扩展，不是重构知识库。视觉模型只做观察；产品确认、型号过滤、来源校验和建单授权仍由已有流程的程序约束负责。现有纯文字请求接口保持可用；图文请求可使用独立输入入口，但必须复用同一会话 ID 和任务状态。视觉模型服务是否可用、是否接受所需图片格式及其成本，要在开发前用一张测试图做真实调用验证；不能默认当前文本模型或 BGE-M3 能看图。

本轮不把用户原图写进知识库或 Git，也不要求把它持久保存到工单。服务端仅在本轮处理图片；会话可保存必要的**文字化可见线索及其来源类型**，供下一轮追问和交接使用。若建立工单，人工可以看到这些文字化线索，但不能被告知“可查看原图”，除非后续单独实现并验证图片存储与权限。日志不得输出原图、密钥或完整图片编码。这是对上层增强设计中“受控本地图片引用”的收紧：本 PRD 的第一阶段先不做原图留存。

## 7. 验收场景与失败边界

| 场景 | 预期结果 |
| --- | --- |
| 清晰的 T2080 标签图＋模糊诉求 | 提取候选型号，仍请用户确认产品；确认后才查 T2080 资料 |
| 同名另一品类或相似型号图 | 不直接套用扫拖机器人排障知识，先核实产品对象 |
| 模糊、遮挡或无关图片 | 承认无法判断，提供重拍或文字补充方式 |
| 图中文字与用户描述冲突 | 展示冲突并追问，不把任一方自动升格为已确认事实 |
| 仅上传图片，没有描述症状 | 可以发送；先询问用户遇到的具体问题，而不是猜测故障 |
| 视觉服务超时、报错或返回无效结构 | 告知图片未分析成功；纯文字任务状态和旧排障链路不丢失 |
| 用户已确认产品并继续反馈 | 仍按原有官方文字资料给一步建议、展示来源并记录反馈 |
| 用户拒绝或重复确认建单 | 原有确认门禁和同会话幂等保持不变 |

验收证据包括：前端上传与错误态录屏、每类测试输入及预期/实际动作、真实视觉模型调用记录（不含图片内容和密钥）、文字回归结果，以及一次图文输入到知识排障的端到端演示。测试图片应有可核对的来源或使用权；不能用未经标注的真实用户私密图片做演示数据。

## 8. 交付顺序与职责

| 检查点 | 看得见的交付物 | 通过条件 |
| --- | --- | --- |
| 0. 基线就绪 | 已验收切片进入正式开发线，文字回归记录 | 图像改造有稳定起点；旧链路未退化 |
| 1. 图片能力验证 | 视觉服务对一张已授权测试图返回结构化可见线索 | 能区分看得见、看不清和失败；成本及调用方式明确 |
| 2. 图文会话 | 页面可选图、预览、移除并提交；服务端把线索交给现有会话 | 图文与纯文字共用任务状态；产品未确认前不查专属知识 |
| 3. 完整回归 | 八类图文边界、原文字测试、图文主链路演示 | 所有安全门禁通过，错误提示与实际状态一致 |

Product Lead（用户）审阅本 PRD、确认演示重点及验收样例；唯一 Technical Builder 在收到**正式交接**后，根据另行细化的实施计划开发并提交测试证据。当前仅写文档，不派发代码任务。初赛版本以 9 月 26 日前稳定演示为准；若视觉服务接入无法在合理时间内验证，停止扩大图片能力，保留已验收的文字切片，不以假图片结果充当多模态交付。
